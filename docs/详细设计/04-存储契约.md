| 项 | 内容 |

| **读端** | 同上 + 大屏 `da_alert.html` + 移动端 |

| **容错** | ⚠️ 见下方两条特例 |
| **广播** | `storage` + `alertStoreChange` |
| **生产替换点** | 同上 |

**⚠️ 两条容错特例（改造必读）**：

```
① 空数组回退缺陷
   inMemory = (stored && stored.length) ? stored : deepClone(DEFAULT_DATA)
   若盘上存的是 []：
     → 内存回退到 46 条默认数据
     → 但 if (!stored) 为假（[] 是truthy）→ 不回写
     → 结果：内存 46 条 / 盘上 0 条，每次刷新都不一致
   修复方案：加载时若为空数组，应写入默认数据或抛错，禁止静默不一致

② 时间戳动态化（不可测试）
   DEFAULT_DATA 在返回前执行 dynamicTimes()：
     按原time 倒序均匀映射到「今天往前 0-29 天」，只保留 HH:mm
   → 首次落盘的时间依赖用户打开当天的日期
   → 快照测试无法断言时间字段
   → 生产环境必须去掉 dynamicTimes()，改由后端下发真实时间
```

#### ST-PMAT-001 `smartorchard_material_store_v1`

| 项 | 内容 |
| --- | --- |
| **管理方** | `MaterialStore`（[material-store.js](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/js/material-store.js)） |
| **结构** | `{ version: 1, materials: Material[] }` — **唯一有 version 包装的 Store** |
| **schema** | CT-MAT-001（23 条 SKU） |
| **写端** | PC 农资 7 页（`material_info` / `material_inventory` / `material_io` / `material_return` / `material_supplier` / `material_usage` / `material_label`） |
| **读端** | 同上 + 移动端 `mb_material.html` |
| **读写时机** | **每次读写都直取localStorage**（无内存缓存） |
| **容量** | 约 6 KB |
| **容错** | `readStored()` 校验 `version === 1 && Array.isArray(materials) && materials.length > 0`，否则用 SEED 覆盖写盘 |
| **广播** | ⚠️ **无自定义事件，无 subscribe** —— 这是与另外 4 个 Store 的最大差异 |
| **生产替换点** | `readStored()` / `persistList()` → REST |

**⚠️ 与其他 4 个 Store 的三处不一致**：

```
① 无 version 语义对齐：另外 4 个 Store 没有 version，本 Store 有
② 无订阅机制：另外 4 个有 subscribe() + CustomEvent，本Store 只能靠页面各自重读
③ 有内存缓存：另外 4 个（BizStore 等）有 inMemory 但监听 storage 同步；
   本 Store 刻意无缓存（因L-3 踩坑），是正确设计
```

> **无订阅机制的影响**：修改库存后，其他已打开的页面不会自动刷新，只能靠用户手动刷新或页面自己 `setInterval` 重读。若需要跨页面实时同步库存，需补一个 `storage` 事件监听 + 自定义事件（参照 `AlertStore` 的 `alertStoreChange`）。列入 `appendix/D` L-D07。

```

remove(key, id)    按 id 过滤
saveList(key, arr) 写盘 + emit(key) 广播
所有读操作：read() 返回 fallback（默认 []），解析失败不抛异常
```

## 3. 容量限制与风险

### 3.1 localStorage 容量

| 项 | 值 |
| --- | --- |
| 单域总容量 | **5 MB**（约 5×10⁶ 字符） |
| 单键容量 | 无独立限制，共享 5 MB |
| 配额溢出表现 | `setItem` 抛 `QuotaExceededError` |

**当前项目总用量**：约 75–95 KB（54 个键），**占容量 < 2%**，无 imminent 风险。

### 3.2 ⚠️ 高风险键

| 键 | 风险 | 原因 | 处置 |
| --- | --- | --- | --- |
| **`cert_stamp_dataurl`** | 🔴 **高** | 存 PNG dataURL，单张签章可达 50–200 KB。base64 比原图大 33%，5 MB 容量下写满 50 MB 就会溢出 | 迁至IndexedDB 或对象存储；过渡期改为只存最近 N 张 |
| **`smartorchard_label_stock`** | 🟡 中 | 键为标签名，改名产生孤儿键，无清理机制 | 改为 id 主键 |
| **`h5_adoption_photos`** | 🟡 中 | 存base64 图片，认养树数量增长后累积 | 迁至IndexedDB |
| **移动端 `photo` 字段** | 🟡 中 | 农事记录、巡查异常的 `photo` 是 dataURL | 压缩后再存（参考 `adoption_photo.html` 的 `compressImage`：长边 ≤1280px、JPEG 起始质量 0.82、超 400KB 逐级降质） |
| **`smartorchard_adoption_tag_archive`** | 🟡 中 | 挂牌 PNG 归档，只存元数据（不含 png），风险低 | 已做容量防护（需求说明书 §30.10） |

### 3.3 容量防护规则（强制）

```
① 写入前估算：新增 dataURL 前计算 totalLength，若超 4 MB 则拒绝并提示
② 图片压缩：所有 <input type="file"> 得到的图片必须经canvas 压缩后存
   参考实现：adoption_photo.html 的 compressImage()
③ 队列上限：smartorchard_sync_queue 超过 500 条时提示用户手动同步
④ 归档只存元数据：png 归档只留 {code, treeNo, adopter, time, size, reason}，不含图片本体
⑤ 捕获异常：所有 setItem 必须 try/catch，溢出时回退为「提示用户清理」而非静默失败
```

## 4. 回退策略（两级，必须实现）

所有数据读取页统一遵循：

```
① 读权威源（Store / localStorage）
        ↓ JSON.parse 失败 / 结构非法 / 类型不符
② 回退内置种子数据（页面内 DEFAULT_xxx 或 Store 的 DEFAULT_DATA）
        ↓
③ 绝不回写权威源
```

### 4.1 ③「绝不回写」为什么重要

**反面教材**：`AlertStore` 恰恰在这里犯了错——空数组回退时 `if (!stored)` 判断为假，导致内存有 46 条默认数据、盘上是空数组，每次刷新都不一致（L-D04）。

**正确做法**：

```javascript
function load() {
  var raw = localStorage.getItem(KEY);
  if (!raw) {
    // 键不存在 → 用种子初始化并落盘（这是唯一允许写种子的场景）
    var seed = deepClone(DEFAULT_DATA);
    save(seed);
    return seed;
  }
  try {
    var parsed = JSON.parse(raw);
    if (!isValid(parsed)) {
      // 键存在但结构非法 → 用种子，但不落盘（保留现场供排查）
      console.warn('[Store] 数据结构非法，回退种子，不覆盖原数据');
      return deepClone(DEFAULT_DATA);
    }
    return parsed;
  } catch (e) {
    // 解析失败 → 同上，保留原始字符串
    console.warn('[Store] 解析失败，回退种子，不覆盖原数据');
    return deepClone(DEFAULT_DATA);
  }
}
```

### 4.2 各Store 的回退实现对照

| Store | 键不存在 | 解析失败 | 结构非法 | 是否回写 |
| --- | --- | --- | --- | --- |
| `BizStore` | ✅ 落盘种子 | ✅ 落盘种子 | N/A | ✅ 允许 |
| `DataStore` | ✅ 落盘种子 | ✅ 落盘种子 | N/A | ✅ 允许 |
| `TraceStatStore` | ✅ 落盘种子 | ✅ 落盘种子 | N/A | ✅ 允许 |
| `AlertStore` | ✅ 落盘种子 | ✅ 落盘种子 | ⚠️ **空数组不一致** | ⚠️ **有缺陷** |
| `MaterialStore` | ✅ 落盘种子 | ✅ 落盘种子 | ✅ 落盘种子 | ✅ 允许 |

> 4 个 Store 的「解析失败 → 落盘种子」虽然与 §4.1 的建议不同（它们会覆盖原数据），但因为原数据已损坏无法恢复，实际影响可控。**接入后端后必须改为不覆盖**，以便保留现场排查。

| 场景 | 时机 | 涉及键 |

### 7.2 snake_case 迁移方案

**执行位置**：[demo-seed.js](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/js/shared/demo-seed.js) 的初始化流程中，**在所有 Store 加载之前执行**。

```
步骤 1  补version：为全部 54 个键统一加version 字段，值= 1
步骤 2  建迁移注册表MIGRATIONS = { key: { from: 1, to: 2, migrate: fn } }
步骤 3  migrateAll() 遍历 MIGRATIONS：
        读 raw → 解析 → 取 version
        version === undefined → 视为 1（存量数据）
        version >= to         → 跳过
        否则 → 执行 migrate(obj) → 写回 → version = to
步骤 4  迁移失败：console.error + 保留原数据 +不写回（禁止覆盖为种子）
```

**迁移函数必须是白名单式，禁止无差别递归**：

```javascript
// 正确：只转换已知的字段名
var FIELD_MAP = {
  createTime: 'create_time', typeName: 'type_name',
  statusText: 'status_text', warehouseCode: 'warehouse_code'
  // ... 完整列表见 03-数据契约.md §1.2
};

function migrateRecord(rec) {
  var out = {};
  Object.keys(rec).forEach(function (k) {
    out[FIELD_MAP[k] || k] = rec[k];   // 未登记的字段原样保留
  });
  return out;
}

// 错误：递归转换所有键（会误伤用户自由文本、若某字段值恰为对象）
function deepConvert(obj) { /*禁止*/ }
```

**迁移分5 阶段**（任务卡 `TC-MIG-001` ~ `TC-MIG-3xx`）：

| 阶段 | 内容 | 前置条件 |
| --- | --- | --- |
| S1 | 迁移函数 + 白名单 + 版本机制 | 无 |
| S2 | 5 个 Store + `MobileBridge` + `MobileStore` + `demo-seed.js` 改造 | S1 完成 |
| S3 | PC 92 页改造（按模块分批） | S2 完成且全量回归通过 |
| S4 | 移动端 33 + H5 16 + 大屏 10 页改造 | S3 完成 |
| S5 | 双形态键统一（`orchard_farming_prefill` 等） | S4 完成 |

> **⚠️ S2 完成后必须全量回归**（151 页全开，检查 console 报错），否则 S3/S4 会出现大面积半改状态。
