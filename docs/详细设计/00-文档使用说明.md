# 00 · 文档使用说明

> **本章作用**：说明本套文档如何被 AI 编程工具与人工开发者消费，以及在信息缺失或冲突时如何行动。
> **本章是全套文档的入口，读完本章再读任何其他章节。**

---

## 1. 为什么需要这份使用说明

AI 编程工具与人类开发者在面对同一份设计文档时，行为模式有根本差异：

| 行为特征 | 人类开发者 | AI 编程工具 |
| --- | --- | --- |
| 遇到空白处 | 主动提问或查代码 | **自行编造一个合理值继续** |
| 遇到冲突 | 追溯设计意图 | **随机选一个，或选择更近的上下文** |
| 改动范围 | 倾向于最小必要改动 | **倾向于"顺手优化"，扩散到相邻文件** |
| 验收 | 理解意图后主观判断 | **无法判断"看起来对不对"，只能跑测试** |
| 记忆边界 | 全局一致 | **上下文窗口外即失忆** |

这张表决定了本套文档的全部设计取向：

- **不留空白** → 每个字段、状态、枚举都必须写死（§3 契约层）
- **不留模糊** → 每个约定都要能判定真伪（`10-前端工程化契约.md`）
- **框定范围** → 任务卡明确"允许改动/ 禁止改动"文件清单
- **可自动判定** → 验收断言写成 Given-When-Then，AI 可自行跑测
- **常驻约束外置** → 硬约束抽成 AI 配置文件，避免依赖上下文记忆

## 2. 标准工作流

### 2.1 人类开发 + AI 辅助（推荐主流程）

```
① 领取任务卡
   ↓
② 读任务卡本身（不读全量文档）
   任务卡已含：目标、契约编号、代码锚点、允许改动文件、禁止事项、验收断言
   ↓
③ 按任务卡标注的契约编号，按需加载 2~4 个契约文件
   例：TC-FARMING-003 → 加载 §3.4 农事记录 + §4.2 农资存储 + §9.2 Pagination + §10.3 script 顺序
   ↓
④ 打开任务卡给出的代码锚点，确认现状
   ↓
⑤ 向 AI 工具下达指令（把任务卡原文 + 契约文件 + 目标文件一起给AI）
   ↓
⑥ AI 产出改动 → 人工审阅 diff → 跑验收断言
   ↓
⑦ 断言全绿 + 浏览器实测无 console 报错 → 提交
```

### 2.2 纯 AI 自动执行（批量任务）

适用于结构高度一致、重复度高的页面（如 92 个 PC 后台列表页）。

```
① 确认这类页面的任务卡是否已存在且契约完整
   ↓
② 一次只交给 AI 一张任务卡，禁止多卡并行写入同一文件
   ↓
③ AI 完成 → 立即跑该卡的验收断言
   ↓
④ 断言失败 → 用原锚点 + 错误信息重试一次；仍失败则挂起，转人工
```

**禁止把 10 张以上任务卡一次性丢给 AI 批量执行。** 批量会让错误累积且互相污染上下文。

## 3. AI 遇到不确定时的行为准则

这是本章最重要的一节。以下规则**优先级高于任何其他章节**，包括任务卡本身。

### 3.1 挂起而非猜测（核心准则）

| 情形 | ❌ 错误做法 | ✅ 正确做法 |
| --- | --- | --- |
| 契约未定义某字段 | 自行取名`status2` / `remark2` | **挂起**，在任务卡回报栏记录「契约缺 XX 字段定义」 |
| 契约未定义某枚举值 | 自行新增「已完成2」 | **挂起**，列出已知的同类枚举，请示是否同源 |
| 不确定某状态能否编辑 | 自行放开编辑 | **保守处理**：按不可编辑实现，并在回报中标注存疑 |
| 不确定两处数据是否同源 | 各自独立读取 | **挂起**，确认是否应共用同一 Store key |
| 找不到任务卡要求的样式类 | 新建一个 CSS 类 | 优先查 `08-设计系统实现契约.md` 是否有现成 token；确实没有才新增，并在回报中说明 |

**判断标准**：如果这个决定会影响**其他页面**或**其他开发者的实现**，就挂起；如果完全局部且可轻易回退，可以自行决定但必须在回报中标注。

### 3.2 改动范围控制

AI 默认具有"扩散改动"的倾向。以下为强制约束：

```
允许改动：任务卡「允许改动文件」清单中的文件
禁止改动：
  - common/**            （公共资源，被 153 个 HTML 共享）
  - js/**  design-system.css / mobile-design-system.css 等设计系统文件
  - 未列入清单的任何 .html 页面
  - 任何 .md 契约文档（除非任务卡明确授权）
```

**为什么禁止改 `common/**`**：该目录被全部 153 个 HTML 共享，改动一处会引发跨端不可预期的连锁故障，且无法通过单页面测试发现。

### 3.3 禁止"顺手优化"

以下行为即使代码质量更高，也**一律禁止**（除非任务卡明确要求）：

| 禁止行为 | 说明 |
| --- | --- |
| 顺手把 `var` 改成 `const`/`let` | 本项目 ES5/ES6 边界见 `01` 章，禁止无差别替换 |
| 顺手给未使用变量补 `console.log` 调试 | 提交前必须清除调试输出 |
| 顺手格式化整个文件 | 会导致 diff 爆炸，掩盖真实改动 |
| 顺手把内联 `<style>` 抽到公共 css | 属于结构重构，须走变更流程 |
| 顺手给其他页面也"修个一样的问题" | 超出任务范围，建新任务卡 |
| 顺手删除"看起来没用"的变量/函数 | 可能被弹窗字符串引用，删除前须全局搜索确认 |
| 顺手统一不同页面的同类写法 | 属`pages/` 层规范，须走变更流程 |

### 3.4 任务完成后的回报格式

每个任务完成后，必须按以下格式回报（这段文字会进入 `14-测试与验收契约.md` 的验证记录）：

```
任务卡：TC-XXX-NNN
完成：  改动了哪些文件、各改了什么
断言：  AC-XXX-NNN-1 PASS
        AC-XXX-NNN-2 PASS
        AC-XXX-NNN-3 FAIL（原因：...）
实测：  浏览器打开 xxx.html，控制台报错数 = 0 / N
存疑：  契约未覆盖的 XX 点，我按 YY 方式处理，请确认
```

**禁止回报"应该没问题""大致完成"这类无法验证的表述。** 断言必须逐条给出 PASS/FAIL。

## 4. 信息优先级与裁决规则

### 4.1 裁决顺序（与 README §4 一致，此处给出可执行判定）

当同一事项在多处有描述且结论不同时，**逐级向下比对，命中即停**：

```
优先级 1  01-技术栈与工程约束.md    硬约束、禁止清单
优先级 2  03~07 契约层                数据/存储/接口/事件/跨端联动
优先级 3  08~12 规范层                设计系统/组件/工程化/权限/部署
优先级 4  pages/ 页面详设             单页面实现约定
优先级 5  html/ 现有代码              现状默认行为
优先级 6  需求说明书 V4.1             产品意图
```

**裁决示例 1**（设计与代码冲突）
> 页面详设写"弹窗使用 Modal 组件"，但现有页面同时引了`common-functions.js` 和 `components/modal.js` 导致报错。
> 裁决：优先级 1 的禁止清单明确规定"禁止同时引用两者" → 遵循禁止清单，删除 `common-functions.js` 引用。

**裁决示例 2**（需求与契约冲突）
> 需求说明书要求"订单状态含已完成"，但 `03-数据契约.md` 的状态枚举只定义了 5 个且不含"已完成"。
> 裁决：契约层优先 → 按 5 个枚举实现，并在回报中标注"需求说明书 §6.2.8 提到'已完成'，契约未收录，请确认是否需要新增枚举"。

**裁决示例 3**（契约与代码冲突）
> 契约说库存字段为 `stock`，但现有 `material_info.html` 读取的是 `qty`。
> 裁决：契约优先 → 改为读 `stock`，并在回报中标注"原代码用 `qty`，已按契约改为 `stock`"。

### 4.2 禁止自行"折中"

发现冲突时，**严禁取两种说法的中间值**。例如契约说字段 `stock`、代码说 `qty`，折中写成 `stock ?? qty` 是严重错误——这会让两个不兼容的约定长期共存，问题被推迟到生产环境才暴露。

正确做法是**选一边，按优先级执行，并记录分歧**。

## 5. 代码标记制的执行规则

页面详设中每一处改造点带一个标记。执行规则：

```
【保留】→ 不触碰。任务中不提及、不"优化"、不"顺手改格式"
【改造】→ 只改标记处指明的那部分，不动同一函数内的其他逻辑
【替换】→ 整段重写，但保持外部调用签名不变
【补齐】→ 新增代码，插入位置在详设中指定
【缺口】→ 新增代码 + 必须补齐对应验收断言
```

### 5.1 一个标记的完整写法

页面详设中每个改造点应写成如下格式，AI 据此定位：

```
【改造】农事记录列表数据源
  位置：farming_record.html#L1200-L1258  renderTable() 调用处
  现状：var mockData = [...]（23 行硬编码数组）
  目标：readRecords() → StorageStore.list(STORAGE_KEYS.FARMING_RECORD)
  契约：§3.4 / §4.2
  约束：保留现有 9 列渲染逻辑与分页调用签名，不得改动列定义
```

四要素缺一不可：**位置、现状、目标、约束**。缺任何一项，AI 都可能扩大改动范围。

## 6. 常见误用与纠正

| 误用 | 后果 | 纠正 |
| --- | --- | --- |
| 让 AI "参考同模块其他页面实现这个页面" | 同模块页面本身可能是错的，错误被复制放大 | 指定参照页面 + 参照**具体区段**（如"参照 `farming_plan.html` 的分页区段"） |
| 让 AI "优化一下这个页面" | 改动不可控，违反禁止清单 | 换成具体任务卡；或明确列出允许改动的具体行 |
| 一次性给 AI 读 10 个契约文件 | 关键约束被稀释，违反项概率上升 | 只给任务卡标注的 2-4 个 |
| 让 AI "按需求说明书实现 XX功能" | 需求说明书无实现细节，AI 会自由发挥 | 让AI 先读对应契约 + 任务卡，需求说明书仅作背景 |
| 未定义验收标准就开工 | 完成度无法判定，反复返工 | 先确认 `14` 章有对应断言 |
| 多个页面并行修改同一共享 js | 后写入的覆盖先写入的 | 共享 js 的修改单独开任务卡，串行执行 |
| 用 AI 生成的字段名直接落库 | 污染存储 schema | 字段名必须来自 `03-数据契约.md` |

## 7. 本章的约束效力

本章规则在整个开发过程中持续生效，效力高于：

- 任务卡中的任何模糊表述（任务卡须服从本章）
- AI 工具的默认行为偏好
- 开发人员临时的便利性考量

**唯一例外**：任务卡明确标注「本卡授权修改 `js/xxx.js`」时，允许改动该文件——但仍不得违反 `01-技术栈与工程约束.md` 的禁止清单。
