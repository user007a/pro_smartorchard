# 移动端 · 模型与认养（MB-020~031）

> **本文件作用**：给出移动端作业端「模型（生长/病虫害/气象/产量/价格）」与「认养（管理/浏览/详情/证书/农事/采收/挂牌）」共 12 页的逐页实现契约，说明每一页当前的 DOM 结构、数据来源、写操作是否真落盘、列表加载形态，以及从原型走向生产必须补齐的改造点。
> **页面范围**：MB-020 ~ MB-031（12 页）
> **源码目录**：`html/applefarm_mobile/`

## 1. 模型与认养

### 1.1 模块概述

**本组共性结论**：

```
① MB-020~MB-024 这 5 个模型页是「零数据源」的纯静态演示：
   全部不引 js/mobile-store.js，全部只有一个 navigateTo() 函数，
   所有数字（95%、450 吨、4.5 元/斤、3/18/105 风险数）直接写死在 HTML 里。
   PC 后台的 model_growth.html / model_pest.html / model_weather.html /
   model_yield.html / model_price.html 同样是内存 mock，
   → 模型类目前「全端无落盘键」，生产化必须先申请新键（见 L-MB3-01）。

② MB-025~MB-031 共 7 个认养页已建立 4 条跨端写链路：
   smartorchard_adoption_tags（MB-029/MB-031 写 → PC adoption_tree/adoption_farming 读）
   smartorchard_harvest_reservations（MB-030 写 → PC adoption_harvest 读）
   h5_sales_orders（MB-025 写 → H5/PC 商城读）
   smartorchard_farming_records（MB-027 读 ← MB-005 mb_record_task 写）
   但只有第 4 条是真正闭环的农事链路，其余 3 条的读端均不完整。

③ 跨端键耦合最严重的是 MB-029：它读 smartorchard_farming_records 的
   「同类数据」却读了硬编码 5 条农事项，而真正读该键的是 MB-027。
   → 用户在 mb_record_task 记录的真实农事，永远不会出现在 MB-029 的勾选列表里
     （L-MB3-08）。

④ 12 页全部没有分页，也没有「加载更多」：
   按 README §0.3 共性约束⑤，移动端/H5 一律「加载更多」或全量渲染；
   但认养浏览的果树列表、认养管理的订单列表在真实数据下会突破 50 条，
   必须补「加载更多」或分页（见 L-MB3-12）。

⑤ 12 页全部没有权限控制（README §0.3 共性约束⑥）：
   认养管理页的「确认发货 / 确认采摘 / 编辑证书」等写操作无任何角色校验，
   任何能打开页面的用户都可执行（L-MB3-13）。

⑥ storage 监听只有 3 页有（MB-026 / MB-028 / MB-031）：
   MB-025 认养管理、MB-029 认养农事 写了共享键却不监听，
   PC 后台改动后移动端不刷新（L-MB3-14）。

⑦ MB-020~MB-024 五页完全没有骨架屏与离线态，只有 MB-021 有一段 600ms 的
   setTimeout 假骨架（mb_pest_risk.html L246-L251）。
   移动端在弱网下会直接白屏，无「加载中 / 离线」任何提示（L-MB3-11）。

⑧ 数字硬编码的「时间语义」在多页重复出错：
   MB-022 预报日期随 JS 滚动但温度不滚；MB-023「更新于 10月21日」固定；
   MB-024「9月21日」固定且标题写「未来6个月」而月份轴只有 4 个月；
   MB-030 日期条固定 2026-09-25~10-01。跨月后全部失真。
```

> **代码生成缺陷**：`makeCode()`（L211-L215）用 `h = (h * 31 + charCode) >>> 0` 求哈希，但 **JS 的 `*` 对超过 2^53 的数会丢失精度**，且 `>>> 0` 只在运算末尾才截断——哈希分布很差，不同 (treeNo, adopter) 组合可能撞码。目标：改用与 MB-028 `seededRand()`（L623-L635）一致的 FNV-1a 实现（`Math.imul`），并把 `code` 加入唯一性校验（撞码时追加序号）。

> **编号口径冲突**：挂牌 `code` 格式为 `AD` + 4 位年份 + 6 位 base36（L214），而订单号格式为 `AD` + 8 位日期 + 3 位序号（MB-025 L517），证书号为 `AD` + 8 位日期 + 3 位序号（MB-028 L479）。三种 `AD` 前缀编号**无统一编码规则**，跨端对账时会误判为同一类单据。目标：定义统一编码段（类型码 + 日期 + 序号），三处同步。

#### 10 边界态

- **空数据**：`renderTagRecords()` 在数组为空时展示「暂无挂牌记录，提交挂牌后将显示在这里」（L236）。目标：同时区分「键不存在」与「主动清空」两种情形（`keyExists()` 范式），并按 kind 过滤掉农事绑定记录。
- **搜索无果**：本页无搜索。目标：搜索无命中时展示「没有匹配的挂牌记录」。
- **字段超长**：`#treeNo`（L125）可输入任意长度，「花牛苹果 #A025」这类长串会溢出 `.tag-title` 与 canvas 的 `ctx.fillText()`（L402，无 maxWidth 约束）。目标：输入框加 `maxlength`，canvas `fillText` 加 `maxWidth`。
- **并发写冲突**：无。目标：同一棵树重复挂牌时提示「该果树已存在有效挂牌，是否覆盖？」并用 `MobileStore.upsert`（`mobile-store.js` L118）而非 `push`（L113 直接 `unshift`，会堆重复记录）。
- **权限不足**：无。目标：仅基地管理员可生成挂牌，且仅能对本基地果树挂牌。
- **离线**：无。目标：离线时**禁止生成挂牌**（PNG 与记录都需同步到服务端），提示「离线状态不可挂牌」。
- **存储配额写满**：`writePngCache()`（L350-L383）有三层兜底：单条 > 300KB 只留元数据（L429/L432）、超过 10 条挤出并归档（L353-L359）、`setItem` 抛异常时清空全部 base64 后重写（L366-L377）。**但第三层兜底会一次性清空所有历史挂牌图片**（L369-L375），且 `MobileStore.push`（L278）在 `writePngCache()` **之前**执行（L278 → L283），若配额已满，`push` 本身的 `saveList()`（`mobile-store.js` L102-L106 → `write()` L73-L81）会静默返回 `false`——**挂牌元数据记录也丢了，用户却仍看到「挂牌生成成功」**。目标：`push` 返回值必须校验，失败时提示并回滚。
- **PNG 图片丢失**：被挤出上限的记录只在列表里显示「图片已归档」（L243），用户无法再下载。目标：归档项提供「重新生成」入口（可重新 canvas 绘制，种子仍为 `code`，图案一致）。
