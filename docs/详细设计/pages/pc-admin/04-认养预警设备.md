# 04 · 认养 / 预警 / 设备 / 证书（21 页）

> **本章作用**：认养 7 页、预警 5 页、设备 7 页、证书 2 页的逐页实现契约。
> **本章最重要的结论**：**认养 4 个列表页（果树/农事/采收/订单）仍以内存 mock 为主，新增与编辑全部 `alert()` 后即结束**；**预警 4 页共享 `AlertStore`，但「预警设置」的规则只存在内存**；**设备模块分成两轨——接入/网关/视频走 `DeviceStore`，设备信息/日志/维护走各自的 25/23/23 条内存数组，两套编号体系（`AC-001` vs `D-001`）无法对齐**；**所谓「证书」在项目里是三套互不相关的实现**。
> **页面编号**：`PC-ADOPT-001~007` / `PC-ALERT-001~005` / `PC-DEV-001~007` / `PC-CERT-001~002`。

### 0.2 四组页面的数据层性质完全不同

```
① 认养 7 页：photo / cert / browse 是「真落盘」的新页面；
   tree / farming / harvest / order 是旧原型，增删改一律 alert() 结束。
   → 不能对 7 页下同一条「接 Store」指令，必须按页区分。
② 预警 5 页：4 页共用一个 AlertStore（真源），
   但 alert_settings 的规则数组是内存变量，只有静默时段与 SLA 两个附属键落盘。
③ 设备 7 页：access / gateway / video 走 DeviceStore（键 applefarm_device_v1）；
   info / log / maintain 是三个互不相干的静态数组，编号 D-001~D-025。
   → 同一个「设备」在不同页有两套编号，跨页跳转必然找不到对象。
④ 证书 2 页：cert_manage 是「质量/检测/产地」合格证；
   cert_issue 是它的打印预览页，但没有任何保存动作；
   而 adoption_cert 是第三套「认养证书」，字段与生命周期完全不同。
```

### 2.1 模块概述

#### 2.1.1 `AlertStore` 公开 API（唯一真源）

| 成员 | 签名 | 消费页面 | 说明 |
| --- | --- | --- | --- |
| `AlertStore.all()` | `() => Alert[]` | 001 | 全量，含 `device` 与 `farming` 两类（`alert_internal_report` 不消费） |
| `AlertStore.byType(type)` | `(type) => Alert[]` | 002 / 003 | 只接受 `'device' \| 'farming'` |

`Alert` 实体字段（改造后按 `03-数据契约` 的 snake_case 对齐）：

#### 2.1.2 三处「词表」互不一致（`L-ALERT-05`）

| 处 | 位置 | 级别取值 |

#### 2.1.3 `alert_settings` 的规则没有消费方

```
规则数组（内存）→ 无任何生成器读取
   ↓ 仅两个附属键真落盘

snzg_alert_sla_config   { urgent|important|reminder|notice: { respond, handle, escalate } }
```
`AlertStore` 里的预警由种子 + 其他页面写入产生，**不经过规则表**；改阈值、删规则都不会让任何预警消失或新增。这是 `TC-ALERT-001` 要解决的核心问题。

## 3. 设备管理（7 页）

### 3.1 模块概述

设备模块是**「两轨制」**最典型的地方：

```
轨 A（真落盘）：device_access / gateway_config / video_monitor
   └ DeviceStore，键 applefarm_device_v1，id 体系 AC-001 / GW-001 / CAM-001
轨 B（纯内存）：device_info / device_log / device_maintain
   └ 各自 25 / 23 / 23 条常量，id 体系 D-001 / L001 / M-001
轨 C（移动端）：mb_device_maintain
   └ MobileBridge.KEYS.maintenance，字段与轨 B 完全不同
```

`DeviceStore` 的字典与默认数据是本模块**唯一的权威定义**：

| 字典 | 内容 |
| --- | --- |
| `DEVICE_TYPES`（7） | 气象监测站 / 土壤墒情仪 / 虫情监测仪 / 监控摄像头 / 环境传感器 / 智能网关 / 水肥一体机 |
| `DATA_POINTS` | 按类型给出物模型测点（气象站 7 项、墒情仪 4 项、虫情仪 3 项、摄像头 4 项、环境传感器 5 项、网关 2 项、水肥机 4 项） |
| `ACCESS_WAYS` | 按类型给出推荐接入方式（MQTT / Modbus TCP / ONVIF / RTSP / GB-T 28181 / HTTPS 回调 / WebSocket） |
| 默认数据 | 接入配置 10 条（`AC-001`~`AC-010`）、网关 5 条（`GW-001`~`GW-005`）、摄像头若干（`CAM-xxx`） |

`device_info` 的 `DEVICE_TYPES` 与 `DeviceStore.DEVICE_TYPES` 字面相同，但**没有共享引用**，各自维护一份，新增类型必然漂移。

## 4. 证书管理（2 页）

### 4.1 模块概述

本模块的两页是**「同一业务的上下游」，但链路是断的**：

```
cert_issue.html（填表 + 打印预览）  --[smartorchard_issued_certs]-->  cert_manage.html（列表 + 作废/续期）
        ↑ 无保存动作（L-CERT-02）              ↑ 只读合并，且有覆盖风险
```

同时它必须与 `adoption_cert.html`（认养证书）区分：后者是「认养关系凭证」，本模块是「农产品质量/检测/产地合格证」，字段、编号规则、生命周期完全不同（`L-CERT-01`）。

#### 4.1.1 两页的字段模型

| 维度 | `cert_manage` 列表实体 | `cert_issue` 表单字段 |
| --- | --- | --- |
| 编号 | `certNo`（`CERT001` 等） | 由批次推导，**无独立编号输入** |
| 类型 | `type`（质量合格证/检测报告/产地证明） | `certTemplate` 模板选择 |
| 批次 | `batchNo` | `certBatch`（`PC-20260901-001`~`020`） |
| 客户/供应商 | `supplier` | 无（模板决定抬头） |
| 有效期 | `validity`（`起 至 止` 单字符串） | 由模板 + 生产日期推导 |
| 状态 | `pending/issued/revoked/expiring` | 无（打印即视为签发） |
| 签章 | 无 | `cert_stamp_dataurl`（canvas 手写签名） |

**有效期用「单字符串」存储**（`'2026-09-01 至 2027-09-01'`），`mergeIssuedCerts()` 靠 `split(' 至 ')` 拆分——任何格式变动都会让 `validStart/validEnd` 变空。
