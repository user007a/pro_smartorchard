# 05 · 经营 / 销售 / 数据运营 / 模型（23 页）

> **本章作用**：经营分析 9 页、销售管理 3 页、数据运营 4 页、模型管理 7 页的逐页实现契约。
> **本章最重要的结论**：**经营 9 页里只有 3 页（收入构成 / 应收周转 / 经营指标）真正读 `BizStore`，其余 6 页的 KPI、图表、表格全部是硬编码常量**，其中两张报表的「导出」还会产出空表或错表；**销售 3 页中只有订单页的发货/催付真正落盘，客户管理 5 个写操作全部 `alert()` 即结束**；**数据运营 4 页以 `DataStore` 为真源，但模型配置页另起两个游离键**；**模型 7 页没有任何 Store，全部是页面内常量**，其中 5 页通过 `orchard_farming_prefill` 与农事计划形成唯一真实链路。
> **页面编号**：`PC-BIZ-001~009` / `PC-SALES-001~003` / `PC-DATA-001~004` / `PC-MODEL-001~007`。

### 0.2 四组页面的数据层性质完全不同

```
① 经营 9 页：三种代际并存
   - 旧报表 4 页（report_overview / revenue / cost / profit）：常量驱动，筛选栏是装饰；
   - 新 Store 3 页（biz_revenue_mix / biz_receivable / biz_metrics）：真读真写 BizStore；
   - 绩效 2 页：看板数据数组与静态表手工对齐；详情页不读参数。
   → 不能对 9 页下同一条「接 BizStore」指令：收入/成本/利润三张报表的粒度（地块/科目/基地）
     在 BizStore 中没有对应实体，必须先补数据契约。
② 销售 3 页：订单页双读 H5 真单 + B 端内存单；客户页纯内存；统计页静态为主。
   → 订单页是唯一「跨端真实链路」，客户页的 5 个写操作全部是 alert()。
③ 数据运营 4 页：data_source / model_monitor 有写操作，data_collection / achievement_record 只读。
   → DataStore 是唯一真源，但 model_config 用两个游离键另起一套模型配置。
④ 模型 7 页：零 Store。5 页的「采纳建议 / 生成防治 / 发布任务」写 orchard_farming_prefill，
   这是模型模块与生产模块之间唯一真实生效的链路。
```

### 1.1 模块概述

经营分析是本项目**统计数据口径最混乱**的模块：同一套「年度总收入」在 4 个页面有 4 个值。

| 口径 | 值 | 出现位置 |
| --- | --- | --- |
| 企业产值 `2512` 万 + 认养收入 | 动态 | `report_overview.loadReportData()`（死写） |
| 年度总收入 `7,530,960` 元 | 常量 | `report_overview` KPI |
| 本月总收入 `378,700` 元 | 常量 | `report_revenue` KPI |
| 年度营收 `2656` 万 | `BizStore.totalRevenue` | `biz_revenue_mix` |

**统一改造方向**：以 `BizStore` 为经营口径唯一真源；报表页的地块/科目粒度数据另建 `BizReportStore`，禁止继续在 HTML 里写常量。
