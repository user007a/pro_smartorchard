# 11 · 权限契约

> **本章作用**：定义角色模型、权限粒度、菜单可见性、数据隔离、鉴权链路。
> **⚠️ 本项目当前权限体系存在 3 个严重缺陷，本章如实记录并给出处置方案。**

## 0. 先看这一节：权限现状的问题

| # | 问题 | 后果 |
| --- | --- | --- |
| **1** | **登录写入 `role`（中文），权限过滤读 `roleCode \|\| role`** | `admin` 中文角色「超级管理员」≠ `admin` → **超管也走过滤** |

## 1. 角色模型

### 1.1 内置 8 个角色

**存储**：`snzg_roles[]`（[system_settings.html](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/system_settings.html#L1192)）

| id | name | code | userCount | desc |
| --- | --- | --- | --- | --- |
| 1 | 超级管理员 | `admin` | 1 | 系统最高权限，可管理所有功能 |
| 2 | 企业管理员 | `enterprise` | 2 | 管理企业信息、基地与地块等基础数据 |
| 3 | 基地管理员 | `manager` | 3 | 管理基地日常运营，可操作农事、采收等 |
| 4 | 农事操作员 | `operator` | 12 | 执行具体农事操作，记录采集数据 |
| 5 | 仓库管理员 | `warehouse` | 1 | 管理农资库存、出入库操作 |
| 6 | 设备管理员 | `equipment` | 1 | 管理 IoT 设备、维护保养 |
| 7 | 营销专员 | `marketing` | 1 | 产品营销、订单与客户管理 |
| 8 | 财务管理员 | `finance` | 1 | 负责财务报表、收支管理 |

**🔴 `id` 类型不统一**：内置为数字 `1`–`8`，新增角色为 `'R' + 时间戳` 字符串（见 `03-数据契约.md` CT-USER-002）。

### 1.2 🔴 角色 code 与登录写入的 role 不一致

**登录页硬编码 5 个账号**（[login.html](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/login.html#L556-L562)）：

| username | password | role（写入 `snzg_user.role`） |
| --- | --- | --- |
| `admin` | `admin123` | **超级管理员**（中文） |
| `manager` | `manager123` | **企业管理员**（中文） |
| `farmer` | `farmer123` | **农事员**（中文） |
| `worker` | `worker123` | **普通农工**（中文） |
| `demo` | `demo123` | 演示账号（`disabled: true`） |

**系统设置页的角色 code**：`admin` / `enterprise` / `manager` / `operator` / …

**🔴 三重不一致**：

```
① 登录写入的是中文 role，权限配置用的是英文 code
② username 'manager' → role「企业管理员」(code 应为 enterprise)，
   但与「基地管理员」(code=manager) 的 code 撞名
③ username 'farmer' → role「农事员」，不在8 个内置角色中
```

### 1.3 🔴 后果：超管也走权限过滤

`index.html` 的过滤逻辑（[index.html](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/index.html#L994-L1041)）：

```javascript
var user = JSON.parse(sessionStorage.getItem('snzg_user') || 'null');
var roleCode = (user && (user.roleCode || user.role)) || 'admin';
var saved = JSON.parse(localStorage.getItem('snzg_permissions') || 'null');
if (!saved || roleCode === 'admin') return;   // 无配置或超管：不做过滤

var hasConfig = Object.keys(saved).some(function (k) {
  return k.split(':')[0] === roleCode && saved[k] === true;
});
if (!hasConfig) return;   // 无配置：不过滤（保持默认全可见）
```

**问题**：

```
① 登录写入 snzg_user.role = '超级管理员'（中文），没有 roleCode
② roleCode 兜底为 '超级管理员'
③ roleCode !== 'admin' → ① 的超管豁免失效
④ 若 snzg_permissions 中配了 '超级管理员:*' 的任何 true → 走过滤逻辑
⑤ 但 system_settings 配的 role code 是 'admin' 等英文
   → hasConfig 判断为 false → 不过滤（侥幸不出错）
```

**净效果**：**超管豁免实际上从未生效**，只是因为权限配置的 role code 是英文而侥幸没暴露。

> **⚠️ 若有人用 `system_settings` 给中文 role「超级管理员」配了权限，超管会被误过滤。** 修复方案见 §7。

## 2. 权限粒度

### 2.1 三层模型

```
① 菜单级：能否看到侧边栏的某一项
② 操作级：能否执行 view / add / edit / delete / export
③ 数据级：能操作哪些基地的数据（当前无实现）
```

### 2.2 操作类型（5 种）

**存储**：`system_settings.html` 的 `PERM_ACTIONS`（[L1751](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/system_settings.html#L1751)）

```javascript
var PERM_ACTIONS = ['view', 'add', 'edit', 'delete', 'export'];
```

| action | 中文 | 对应页面操作 |
| --- | --- | --- |
| `view` | 查看 | 列表页查看、详情弹窗 |
| `add` | 新增 | 新建按钮 |
| `edit` | 编辑 | 编辑按钮、表单修改 |
| `delete` | 删除 | 删除按钮、批量删除 |
| `export` | 导出 | 导出按钮 |

### 2.3 🔴 操作模块名与菜单名不一致

**存储**：`PERM_MODULES`（[L1750](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/system_settings.html#L1750)）

  '采收管理', '认养管理', '模型中心', '销售订单', '任务分配', '系统设置'

```

**🔴 三个问题**：

```
① 只有 12 个模块，而实际有 16 个一级菜单 / 90 个已注册导航页（实测自 `index.html` L660-L766 `MENU_GROUP_MAP`；另有 4 页未注册进菜单）

   实际菜单是「模型管理」「预警管理」「销售管理」
③ 模块名是中文的「功能域」，而菜单名是「页面名」

## 3. 权限存储

### 3.1 现状：`snzg_permissions` 双 key 空间

**存储键**：`snzg_permissions`（对象型）

```
格式① 操作级：  '{roleCode}:{module}:{action}'    → boolean
     例： 'admin:农事计划:edit' → true

格式② 菜单级：  '{roleCode}:{菜单名}'               → boolean
     例： 'admin:生产管理' → true
     例： 'admin:生产管理:农事计划' → true
```

**写入方**：

| 位置 | 写入格式 | 说明 |
| --- | --- | --- |
| `system_settings.html:1777` `savePermission()` | 仅格式① | 保存 12×5 = 60 个复选框状态 |
| `index.html:1000` 消费 | 仅格式② | 读菜单可见性 |

> **🔴 关键矛盾**：`system_settings` **只写格式①**，而 `index.html` **只读格式②**。
> 也就是说：**当前权限配置界面保存的权限，对菜单可见性完全无效。**

**同时**：未勾选的项也会显式写入 `false`（[L1776](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/system_settings.html#L1776)）：

```javascript
Object.keys(all).forEach(function (k) { if (!(k in perms)) perms[k] = false; });
```

这意味着单个角色的配置是**完整 60 项**（true/false 都有）。

### 3.2 `snzg_user_accounts` 与 `snzg_user_states`

**存储键**：`snzg_user_accounts`（对象型）

```
{ [username]: { password, realName, role, phone, disabled, gender?, email?, dept?, position?, bio? } }
```

**问题**：

```
① password 明文存储
② 与 snzg_passwords 重复存储同一份密码
③ disabled 字段与 snzg_user_states[username] 重复
④ role 存中文，与 snzg_roles.code（英文）不一致
```

**存储键**：`snzg_user_states`（对象型）

```
{ [username]: 'active' | 'disabled' }
```

## 4. 菜单可见性契约

### 4.1 过滤逻辑（三段式）

```
第 1 段：无权限配置 → 不过滤
         if (!saved || roleCode === 'admin') return;

第 2 段：该角色无任何 true 项 → 不过滤（保持默认全可见）
         hasConfig = 存在 k.split(':')[0] === roleCode && saved[k] === true
         if (!hasConfig) return;

第 3 段：白名单模式
         key = '{roleCode}:{一级菜单}:{页面名}'
         menuKey = '{roleCode}:{一级菜单}'
         allowed = (key in saved) ? saved[key]
                                 : ((menuKey in saved) ? saved.menuKey : false)
         → 未列出的一律隐藏
```

**第 2 段的设计意图**：避免「漏配即全禁」——新角色未配置时保持全可见。

**第 3 段的分组隐藏**：

```javascript
// 逐个分组检查：若该分组下已无任何可见子项，则连分组标题一起隐藏
document.querySelectorAll('.sidebar-nav .menu-items').forEach(function (box) {
  var visible = [...box.querySelectorAll('a[href]')].filter(x => x.style.display !== 'none');
  if (visible.length) return;
  var head = box.previousElementSibling;
  if (head) head.style.display = 'none';
  box.style.display = 'none';
});
```

### 4.2 `MENU_GROUP_MAP`（页面 → 一级菜单）

**位置**：`index.html` L657 起，**硬编码的 89 项映射表**

```javascript
const MENU_GROUP_MAP = {
  'enterprise_info.html': '企业管理',
  'farming_plan.html': '生产管理',
  // … 89 项
};
```

**🔴 覆盖缺口（实测）**：侧栏共 **93 个 `<a>` 链接**，但 `MENU_GROUP_MAP` 只有 **89 项**，缺 4 项：

| 缺失页面 | 应归属 | 后果 |
| --- | --- | --- |
| `home.html` | —（首页，无需） | ✅ 无影响 |
| `device_access.html` | 设备管理 | ⚠️ 面包屑只显示两级；权限 key 的 group 为空串 |
| `gateway_config.html` | 设备管理 | 同上 |
| `video_monitor.html` | 设备管理 | 同上 |

**⚠️ 影响**：这 3 个设备管理页面的面包屑退化为「首页 › 页面名」（丢失一级菜单层级），且权限过滤时 `group = ''` 会构造出 `roleCode::页面名` 这样的畸形 key。

**修复**：

```javascript
const MENU_GROUP_MAP = {
  // … 现有 89 项 …
  'device_access.html': '设备管理',
  'gateway_config.html': '设备管理',
  'video_monitor.html': '设备管理'
};
```

> **⚠️ 新增页面时必须同步更新此表**，否则面包屑与权限过滤都会退化。建议改为从导航 DOM 自动生成（见 §7）。

### 4.3 🔴 菜单隐藏 ≠ 权限控制（安全缺陷）

**当前实现**：仅在 `index.html` 中对侧边栏 `<a>` 元素设置 `style.display = 'none'`。

**🔴 绕过方式**（三条）：

```
① 直接在地址栏输入 applefarm_backhand/farming_plan.html
   → 子页面无任何守卫（登录守卫只在 index.html）→ 直接可访问
② 通过 parent.openPage('farming_plan.html', '农事计划') 从控制台调用
③ 页面内已有的其他跳转入口（如面包屑、快捷入口）
```

**根因**：登录守卫只在 `index.html`（L13），子页面不重复守卫（`02-架构总览.md` §1.3 已声明这是有意设计）。

**生产修复方案**：

```
① 每个子页面在 <head> 内检查 sessionStorage['snzg_logged_in']（轻量，10 行内）
② 子页面检查当前页面是否在 MENU_GROUP_MAP 中且该角色有权限
③ 或改为单页应用（不再用 iframe）
```

**过渡期方案**（本批次推荐）：在 `iframe-hide.js` 中增加权限检查——因为它已在每个子页面加载：

```javascript
// js/iframe-hide.js 内追加
(function guard(){
  if (window.self === window.top) return;   // 独立打开时也需检查
  if (sessionStorage.getItem('snzg_logged_in') !== '1') {
    window.location.replace('login.html');
  }
})();
```

> ⚠️ 这需要单独任务卡，因为 `iframe-hide.js` 是 95 个页面共享的文件。

## 5. 改造方案：`snzg_permissions` 拆为两个键

### 5.1 目标结构

```
snzg_permissions    操作级  { [roleCode]: { [module]: { [action]: boolean } } } }
snzg_role_menus     菜单级  { [roleCode]: { [menuGroup]: { [menuName]: boolean } } } }
```

**优势**：

```
① 两套 key 空间物理隔离，删除时不会漏
② 嵌套结构直观，不需要 split(':') 解析
③ 角色为一级 key，便于批量查询/删除
```

### 5.2 数据迁移

```javascript
/**
 * 一次性迁移：把旧的扁平 key 拆为两个新键
 * 写入 localStorage，幂等
 */
function migratePermissions() {
  var KEY_OLD = 'snzg_permissions';
  var KEY_OP  = 'snzg_permissions_v2';
  var KEY_MENU= 'snzg_role_menus_v1';
  var FLAG = 'snzg_perm_migrated';

  if (localStorage.getItem(FLAG) === '1') return;   // 已迁移
  var old = {};
  try { old = JSON.parse(localStorage.getItem(KEY_OLD) || '{}') || {}; } catch (e) {}

  var op = {}, menu = {};
  Object.keys(old).forEach(function (k) {
    var parts = k.split(':');
    if (parts.length === 3) {
      // 格式①：role:module:action
      var role = parts[0], module = parts[1], action = parts[2];
      op[role] = op[role] || {};
      op[role][module] = op[role][module] || {};
      op[role][module][action] = !!old[k];
    } else if (parts.length === 2) {
      // 格式②：role:menuGroup 或 role:menuGroup:menuName
      var r = parts[0], g = parts[1], n = parts[2];
      menu[r] = menu[r] || {};
      if (n) {
        menu[r][g] = menu[r][g] || {};
        menu[r][g][n] = !!old[k];
      } else {
        menu[r][g] = menu[r][g] || true;    // 分组级授权
      }
    }
  });

  try {
    localStorage.setItem(KEY_OP, JSON.stringify(op));
    localStorage.setItem(KEY_MENU, JSON.stringify(menu));
    localStorage.setItem(FLAG, '1');
    console.info('[权限] 已迁移到 v2 结构：', {op: Object.keys(op), menu: Object.keys(menu)});
  } catch (e) {
    console.error('[权限] 迁移失败，保留原数据', e);
    // ⚠️ 不设 FLAG，下次登录会重试
  }
}
```

**迁移位置**：`index.html` 的登录守卫之后、权限过滤之前（因为该逻辑已在 `<head>` 内联脚本中）。

### 5.3 新的读写契约

**写（`system_settings` 的权限配置界面）**：

```javascript
// 保存操作级
var op = JSON.parse(localStorage.getItem('snzg_permissions_v2') || '{}');
op[role] = op[role] || {};
PERM_MODULES.forEach(function (m) {
  op[role][m] = op[role][m] || {};
  PERM_ACTIONS.forEach(function (a) {
    var cb = document.querySelector('input[name="perm"][value="' + role + ':' + m + ':' + a + '"]');
    op[role][m][a] = cb ? cb.checked : false;
  });
});
localStorage.setItem('snzg_permissions_v2', JSON.stringify(op));
```

**读（`index.html` 的菜单过滤）**：

```javascript
var menus = JSON.parse(localStorage.getItem('snzg_role_menus_v1') || '{}');
var roleMenus = menus[roleCode] || null;

document.querySelectorAll('.sidebar-nav a[href]').forEach(function (a) {
  var url = a.getAttribute('href');
  var name = (a.querySelector('span:last-child') || a).textContent.trim();
  var group = MENU_GROUP_MAP[url] || '';
  if (!roleMenus) return;                       // 该角色无菜单配置 → 全可见
  var groupCfg = roleMenus[group];
  if (groupCfg === true) return;                // 分组级授权 → 全可见
  var itemCfg = groupCfg && groupCfg[name];
  if (itemCfg === false) a.style.display = 'none';
  // ⚠️ 未列出时保持可见（黑名单模式）或隐藏（白名单模式）
});
```

### 5.4 白名单 vs 黑名单（需决策）

| 模式 | 规则 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **白名单**（现状） | 未列出即隐藏 | 权限收紧 | 新增页面默认不可见，需手动授权 |
| **黑名单** | 仅列出 `false` 才隐藏 | 新增页面默认可见 | 权限收紧需手动配置 |

**推荐**：分组级用白名单（`roleMenus[group] === true` 才全可见），项级用黑名单（仅 `false` 隐藏）。这样新增页面在已授权分组下自动可见，减少配置负担。

## 6. 数据级权限（当前无实现）

### 6.1 现状

**用户表有 `base` 字段**（基地隔离维度）：

```javascript
{ id: 2, username: 'huijianing', role: 'manager', base: '天水麦积区基地', … }
{ id: 4, username: 'xushuiying',  role: 'operator', base: '招远基地', … }
```

**但**：

```
① snzg_user 中不存 base（只有 username/realName/role/loginAt）
② 页面读取数据时不过滤 base
③ 多基地数据混在一起展示
```

**需求说明书 §7.4 已声明多基地隔离是设计要求**（见 `07-跨端联动契约.md` §4 的隔离维度表）。

### 6.2 目标：按基地过滤

```javascript
// 登录时写入 base
sessionStorage.setItem('snzg_user', JSON.stringify({
  username: 'huijianing',
  realName: '惠加宁',
  role: '基地管理员',
  roleCode: 'manager',        // 🔴 新增：英文 code

  loginAt: Date.now()
}));

// 页面读数据时过滤
function canAccessBase(baseName) {
  var u = JSON.parse(sessionStorage.getItem('snzg_user') || 'null');
  if (!u || u.roleCode === 'admin') return true;      // 超管全通
  return (u.bases || []).indexOf(baseName) >= 0;
}
```
