### 1.3 PC 后台外壳机制（关键架构约束）

PC 后台**不是独立页面跳转**，而是 `index.html` 单页外壳 + iframe 容器：

```
index.html
  ├── <head> 内联登录守卫（读 sessionStorage['snzg_logged_in']）
  ├── 左侧固定侧边栏（16 个一级菜单 + 90 个 <a> 链接）
  ├── openPage(file, title) → 更新 iframe.src + 面包屑 + 高亮当前项
  └── <iframe name="mainFrame">
        └── 加载 enterprise_*.html / farming_*.html 等 90 个页面
```

**架构含义（直接约束开发）**：

| 约束 | 说明 |
| --- | --- |
| 页面不能依赖 URL query 传参 | iframe 切换会丢失 query |
| 页面不能依赖 `window.opener` / `window.parent` 做业务 | 仅可用于面包屑等外壳通信 |
| 页面间跳转必须用 `parent.openPage(...)` | 直接改 `location.href` 会跳出外壳 |
| 登录守卫只在 `index.html` 做 | 子页面**不需要**重复守卫 |
| 子页面不得自行渲染侧边栏与顶栏 | [iframe-hide.js](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/js/iframe-hide.js) 会在 iframe 中自动隐藏 `.sidebar` / `.topbar` / `.sidebar-overlay`，并让 `.main-wrapper` 撑满。该脚本以 `window.self === window.top` 判断，仅在 iframe 中生效，独立打开时不做任何事 |
| 子页面高度由 iframe 自适应 | 不要写死 `height: 100vh` |

### 2.4 各 Store 统一的 API 形态

六个 PC 共享 Store（`BizStore` / `DataStore` / `TraceStatStore` / `AlertStore` / `DeviceStore` / `MaterialStore`）遵循同一套模式：

```
读取：  Store.xxx()                返回 deepClone，调用方无法污染内部
写入：  Store.setXxx() / upsertXxx() / applyDelta() / updateStatus()
订阅：  Store.subscribe(fn)        注册即回调一次首屏数据，返回 unsubscribe
重置：  Store.reset()              恢复种子数据
广播：  写入后派发 storage 事件 + 自定义 CustomEvent
```

**统一自定义事件名**（5 个 Store 各一个，均为 `xxxStoreChange`）：

| Store | 事件名 | detail 结构 | 派发位置 |
| --- | --- | --- | --- |
| `BizStore` | `bizStoreChange` | `{ reason }` | `biz-store.js` L187 |
| `DataStore` | `dataStoreChange` | `{ reason }` | `data-store.js` L153 |
| `TraceStatStore` | `traceStatStoreChange` | `{ reason }` | `trace-stat-store.js` L149 |
| `AlertStore` | `alertStoreChange` | `{ reason }` | `alert-data.js` L182 |
| `DeviceStore` | `deviceStoreChange` | `{ reason }` | `device-store.js` L347 |
| `MaterialStore` | ⚠️ **无** | — | — |

**模式完全一致**（5 个有事件的 Store）：`broadcast(reason)` → 先 `save()` 落盘 → `notify(reason)` 通知同页订阅者→ 再 `dispatchEvent(CustomEvent)` 通知同窗口内的其他文档（含 iframe）。

> `storage` 事件**不会在当前窗口触发**，只通知其他标签页/窗口。因此同页多订阅者必须靠 `subscribe()` 或自定义事件，不能只监听 `storage`。

> ⚠️ **`MaterialStore` 是唯一没有订阅机制的 Store**，详见 `04-存储契约.md` ST-PMAT-001 与遗留问题 L-D07。

详见 `06-事件契约.md`（批次 2）。

## 3. 依赖方向规则（最重要的一节）

### 3.1 允许的依赖

```
页面 ──读取──▶ Store（单向下游）
页面 ──读取──▶ 公共资源（css / icons / vr-hotspots）
移动端页面 ──写入──▶ MobileStore 的key
PC 页面     ──读取──▶ MobileBridge（而非直接读 key）
大屏页面    ──读取──▶ PC 的 4 个 Store（BizStore/DataStore/TraceStatStore/AlertStore）
             ▶ DeviceStore（设备接入数据）
H5 页面     ──读取──▶ 自身 h5_* 数据层 + H5Auth
```

### 3.2 禁止的依赖

| 禁止 | 原因 |
| --- | --- |
| Store → 页面 | 数据层不应知道谁在用|
| 页面A → 页面B 的局部变量 | 无稳定契约，随改动即失效 |
| 页面 A 直读 页面 B 负责写入的 key（绕过 Store/桥接） | 绕过回退策略与广播机制 |
| PC 页面直读 `smartorchard_*` 移动端 key | 必须经 `MobileBridge`，否则字段映射丢失 |
| 移动端页面读 `applefarm_*` PC key | 移动端不消费 PC 数据 |
| 大屏页面写入任何 Store | 大屏是**只读消费端** |
| H5 页面读 PC/移动端 key | C 端与作业端数据隔离 |

### 3.3 大屏的只读定位

数据大屏（`applefarm_dataanlye/`）是**纯展示端**，只从 PC Store 读取：

```
BizStore      → da_business.html（收入构成/成本/应收/指标）
DataStore     → da_results.html（数据源/归集/模型监控/成效）
TraceStatStore→ da_trace.html（扫码/地域/渠道/上链）
AlertStore    → da_alert.html（预警总览）
DeviceStore   → da_iot.html（设备接入/网关/视频通道，若已接入）
```

**大屏绝不调用任何 `setXxx` 方法。** 若某个大屏页面需要展示的数据当前没有 Store 支撑，正确的做法是新增/扩展 Store（在PC 端维护），而不是让大屏自己存一份。

## 4. 页面内部结构约定

### 4.1 PC 后台页面的标准骨架

```
<page-shell>
  ├── page-header            标题 + 面包屑（三级，由外壳提供）
  ├── data-section           ← 内容卡片容器（统一 class）
  │     ├── search-bar           筛选区
  │     ├── action-bar           操作按钮区
  │     ├── data-table-wrapper   表格包裹（统一 class）
  │     │     └── table
  │     └── #pagination-container 分页容器（统一 id）
  └── modal-root             弹窗挂载点
```

**统一容器约定：目标态（新建页面必须遵循）**

| class / id | 用途 | 目标态 |
| --- | --- | --- |
| `data-section` | 内容卡片容器 | 新页面必须使用 |
| `data-table-wrapper` | 表格横向滚动包裹 | 有表格的页面必须使用 |
| `pagination-container` | 分页挂载点（id） | 有分页的页面必须使用，且须在 `data-section` **内部** |
| `search-bar` | 筛选区 | 有筛选的页面必须使用 |
| `action-bar` | 操作区 | 有操作的页面必须使用 |

**⚠️ 现状覆盖率（实测 95 个 PC 页面）**

| 容器 | 已使用页面数 | 覆盖率（/95） | 处置 |
| --- | --- | --- | --- |
| `data-section` | 72 | 76% | 存量缺的要补，新页面必用 |
| `data-table-wrapper` | 65 | 68% | 同上 |
| 搜索区（`search-bar` 及其他命名） | 66 | 69% | 同上 |
| `action-bar` | 40 | 42% | 同上 |
| **`id="pagination-container"`** | **26** | **27%** | ⚠️ 见下方说明 |

> **分页容器 id 存在 4 种历史变体**，这是本项目最普遍的 DOM 遗留问题：
>
> | id 实际取值 | 页面数 | 处置 |
> | --- | --- | --- |
> | `pagination-container` | 26 | ✅ 标准，作为改造目标 |
> | `paginationInfo` | 7 | 🔶 改造时统一为 `pagination-container` |
> | `pagination` | 6 | 🔶 同上 |
> | `paginationContainer` | 1 | 🔶 同上 |
>
> 另：`Pagination.render()` 全站仅 **1 处**被调用，绝大多数页面的分页是各页面自行实现的 `renderPagination()`。**这是历史事实，不是推荐做法。** 改造页面时统一走 [page-actions.js](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/js/page-actions.js#L371-L391) 的内部实现，不要自行另写第三套。

**统一规则（不可违反）**：

```
① 分页组件必须位于 data-section 卡片内部，不得放在卡片外部
② 新增页面的分页容器 id 必须是 pagination-container
③ 存量页面改造分页时，把 4 种变体统一为 pagination-container
④ 分页显示格式统一为：‹ 1 2 3 › 第 X 页/共 Y 页，共 Z 条记录
⑤ 按钮区不显示记录条数，记录条数只在底部分页栏体现
```

> 规则 ① ⑤ 已在项目 memory 中固化（巡园管理、农事标准、基地管理、任务分配均因此调整过）。

## 7. 生产替换点清单

本项目**无后端**这一事实，在代码层面已收敛为若干明确的替换点。接入真实后端时只需替换这些点，**页面调用处无需改动**：

| # | 替换点 | 位置 | 替换内容 |
| --- | --- | --- | --- |
| 1 | Store 的 read/write | 5 个 PC Store | localStorage 读写 → REST 调用 |
| 2 | Store 的 subscribe | 5 个 PC Store | 事件回调 → WebSocket / SSE 推送 |
| 3 | `MobileStore.simulateUpload()` | `mobile-store.js` | `setTimeout(400)` 模拟 → `fetch` 真实提交 |
| 4 | 登录凭据校验 | 各端登录页 | 本机校验 → 服务端校验 + 令牌 |
| 5 | 病虫害识别 | `mb_disease.html` | 像素规则匹配 → 服务端模型推理 |
| 6 | 文件上传 | 各端 | base64 存localStorage → 对象存储直传 |

> 队列、状态栏、重试、去重逻辑在 `MobileStore` 中已收敛为稳定调用面（`enqueue/flush/pending/subscribe`），**替换 `simulateUpload` 一处即可**，其余不动。

## 8. 已知架构边界（不是缺陷）

| 编号 | 边界 | 性质 | 解决时机 |
| --- | --- | --- | --- |
| L-1 | 跨端联动依赖同源 localStorage + `storage`事件，换设备/浏览器即失效 | 「无构建纯静态可双击打开」前提下的固有约束 | 接入后端（替换点 1-3） |
| L-9 | 离线队列「上传」由 `setTimeout` 模拟，无真实请求 | 同上 | 接入后端（替换点 3） |
| L-10 | 品种代码语义在历史演进中不统一 | 数据问题，非架构问题 | 已由需求说明书 §30.13 收敛 |
| L-12 | 巡园无「基地」维度 | 已补齐| 已由需求说明书 §30.14 修复 |

**这四条不得作为 bug 修复**。任何"修复"跨端不生效、离线队列不上传"的提交都应被拒绝——那是设计边界，不是缺陷。
