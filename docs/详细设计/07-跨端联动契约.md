# 07 · 跨端联动契约

> **本章作用**：定义每一条跨端数据链路的**写端、读端、映射规则、隔离维度、失效边界**。
> **本章是本项目最容易出错的地方。** 移动端写的，PC 读不到；不同基地的同名点位状态串了；两端字段名不一致——这些问题的根源都在本章。
> **跨端联动出问题先查本章，不要猜。**

---

## 0. 跨端联动的根本边界（先读这一节）

### 0.1 为什么本项目能做到跨端联动

```
四端运行在同一浏览器、同一域名下
        ↓
共享同一个 localStorage
        ↓
写入后其他页面通过 storage 事件 / MobileBridge 读到
```

### 0.2 ⚠️ 三个必然失效的场景（不是 bug）

| 场景 | 后果 | 原因 |
| --- | --- | --- |
| **换设备**（手机 → PC） | 完全失效 | localStorage 按浏览器实例隔离 |
| **换浏览器**（Chrome → Edge） | 完全失效 | 同上 |
| **不同源**（`localhost` vs `127.0.0.1` vs 线上域名） | 完全失效 | localStorage 按 origin 隔离 |
| **无痕/隐私模式** | 写入失败或丢失 | 浏览器限制 |
| **两个 iframe 互相通信** | ❌ **收不到** | `storage` 事件**不跨 iframe 上下文** |

> **⚠️ 最后一个是本项目的关键技术点**：PC 后台是 `index.html` + iframe 结构，iframe 内页面写入的数据，**父页面和兄弟 iframe 都收不到 `storage` 事件**。这正是 `Store 自定义事件`（`xxxStoreChange`）存在的原因——`dispatchEvent` 在同窗口内跨文档有效。**改造时若把自定义事件删掉只留 `storage`，PC 后台的跨 iframe 联动会全面失效。**

### 0.3 生产环境的解决方案

接入后端后，所有跨端联动改为服务端数据，前端不再依赖 localStorage。**页面层调用处无需改动**，只需替换 Store 的 `read/write/subscribe` 实现（见 `04-存储契约.md` §8）。

## 2. 链路详解

### XC-FARM-001 农事记录回传

```
移动端                          PC 后台
mb_record_task              MobileBridge.farmingRecords()      farming_record.html
  ↓ MobileStore.push()          ↓
smartorchard_farming_records[]
```

**存储键**：`smartorchard_farming_records[]`（ST-MOB-002）

**字段映射（移动端 → PC 表格结构）**：

| --- | --- | --- |
| `id` | `id` | 缺失时兜底 `'MOB-' + idx` |
| `base` | `base` | 缺失时兜底 `'天水麦积区基地'` |
| `plot` | `plot` | 缺失时兜底 `'未指定'` |

| `createTime` | `date` | ISO → `'yyyy-MM-dd'` |
| `createTime` | `time` | ISO → `'HH:mm'` |
| `status` | `status` | 原文 |
| `auditRemark` | `auditRemark` | **PC 回写字段** |
| `remark` | `remark` | 原文 |
| `gps` | `gps` | 嵌套对象，原文 |
| `photo` | `hasPhoto` | **转布尔**：`!!r.photo` |
| — | `source` | **恒为 `'mobile'`** |

**`TYPE_MAP` 移动端农事类型 → PC 类型枚举**（[mobile-bridge.js](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/js/shared/mobile-bridge.js#L45-L51)）：

| 移动端 taskType | → PC `type` |
| --- | --- |
| 疏果 / 套袋 / 环剥 / 除草 / 授粉 / 修剪 / 疏花疏果 | `tool` |
| 喷药 / 病虫害防治 / 杀菌 | `pesticide` |
| 灌溉 / 浇水 | `irrigation` |
| 施肥 / 追肥 / 基肥 | `fertilizer` |
| 其他（未在映射表） | `tool` |

**隔离维度**：**无隔离**。所有基地的农事记录在同一列表中，靠 `base` 字段区分。若 PC 端要做基地筛选，需读 `base` 字段（当前 `MobileBridge` 已提供）。

**失效边界**：移动端与 PC 不同浏览器/设备时失效。

### XC-PATROL-001 巡查打卡回传 ⚠️ 最需注意

```
移动端                          PC 后台
mb_patrol                   MobileBridge.patrolRecords()         farming_patrol.html
  ↓                            ↓
smartorchard_patrol_records[]   （过滤 !r.kind，即排除异常上报）
```

**存储键**：`smartorchard_patrol_records[]`（ST-MOB-003）

**⚠️ 隔离维度：基地 + 点位 id**（需求说明书 §30.14 / L-12 修复项）

**这是本项目唯一有复合隔离维度的链路**，原因是：不同基地可能有**同名点位**（如两个基地都有「南门」），若只按点位名存储打卡状态，会导致 A 基地打卡后 B 基地同��点位显示已打卡。

**已打卡状态的存储键规则**：

```javascript
// 移动端 mb_patrol.html
function checkinKey(base, checkpointId) {
  return base + '::' + checkpointId;   // 例如 '麦积区基地::CP-A01'
}
```

**规则**：

```
① 已打卡状态按「基地 + 点位 id」复合键存储，禁止只用点位名
② 基地选择器变更时，筛选对应基地的巡园路线
③ 路线数据无 base 字段时，降级为不隔离（兼容旧数据）
④ 打卡记录本身（smartorchard_patrol_records）仍不带基地维度，
   靠 checkpointId 关联到路线后推断基地
```

**打卡记录字段**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | `patrol_{checkpointId}_{ts}` |
| `checkpointId` | string | 点位 id |
| `checkpointName` | string | 点位名称 |
| `lat` / `lng` / `accuracy` | number | ⚠️ **扁平定位**（与农事的 `gps` 嵌套不同） |
| `checkinTime` | string | ISO |
| `operator` | string | — |
| `source` | string | `'mobile'` |
| `distance` | number | 距离 |
| `track` | array | 轨迹点 |

**巡园路线配置**（PC `patrol_route.html` 维护，key `mb_patrol_routes`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `routeId` | string | 路线 id |
| `routeName` | string | 路线名 |
| `base` | string | ⚠️ **所属基地**（隔离依据） |
| `points` | array | `{id, name, lat, lng, nearRadius, required, order}` |
| `enabled` | boolean | 是否启用 |
| `remark` / `updatedAt` | string | — |

**其他移动端 key**：`mb_patrol_base`（当前选中基地，字符串）

**失效边界**：换设备失效；路线无 `base` 字段时降级为不隔离。

## 3. 双向回写契约（PC 审批 → 移动端可见）

移动端写入的记录初始 `status` 多为 `pending`，PC 后台处置后需回写到同一条记录。

**唯一回写通道**：`MobileBridge.updateRecord(key, id, patch)`

```javascript
/**
 * @param {string} key   存储键
 * @param {string} id    记录 id
 * @param {object} patch 要更新的字段
 * @returns {boolean}   是否找到并更新成功
 */
```

**已知的回写场景**：

| 链路 | 回写字段 | 触发页面 |
| --- | --- | --- |
| XC-FARM-001 | `status` / `auditRemark` | `farming_record.html` |
| XC-LABEL-001 | `status` / `printTime` / `printBatch` / `approveRemark` | `material_label.html` |
| 设备维护 | `status` / `statusText` / `handleTime` / `handleRemark` | `mb_device_maintain.html` |

**⚠️ `updateRecord` 的三个限制**：

```
① 只按 id 匹配，找不到返回 false，不报错
② 直接改 localStorage 中的数组，不触发 storage 事件
   → 其他标签页不会自动刷新，需手动重读
③ 无字段校验，patch 可以写入任意字段
```

**时间戳工具**：`MobileBridge.stampNow()` 返回 `'yyyy-MM-dd HH:mm'` 本地文本，用于回写时间字段。

## 6. 跨端改造的强制规则

任何涉及跨端数据的改动，必须遵守：

```
① 禁止在页面中直接读另一个端写入的 key
   → PC 读移动端数据必须经MobileBridge
   → 移动端写必须经 MobileStore.push/upsert
② 新增跨端字段前，先在 03-数据契约.md 双端登记
③ 字段映射表（TYPE_MAP 等）改动时，必须同步更新本章
④ 涉及隔离维度的字段（如 base）改动时，必须检查所有打卡/挂牌状态
⑤ 状态枚举改动时，必须全局搜索所有读写方
⑥ 禁止在 storage / 自定义事件回调里写入同一个 key（循环广播）
```

## 8. 跨端一致性验收清单

任何跨端链路的改动，验收时必须逐条实测：

```
□ 移动端写入 → PC 端能读到（同一浏览器同一origin）
□ PC 端回写 → 移动端刷新后能读到
□ 不同基地/用户的数据不串台
□ storage 事件在 PC 后台 iframe 结构下生效
□ 自定义事件（xxxStoreChange）在 iframe 间生效
□ 刷新页面后数据不丢失
□ 解析失败时回退种子，不覆盖真实数据
□ 换设备后数据不存在（符合预期，不是 bug）
□ 状态枚举两端一致（无中英文混用）
□ 控制台无报错
```
