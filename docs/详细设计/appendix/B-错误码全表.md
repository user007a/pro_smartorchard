# 附录 B · 错误码全表

> **本章是 `05-接口契约.md` §1.2 的完整展开**，供后端与前端共同查阅。
> **⚠️ 当前项目无后端，本表为「未来态」约定。** 前端可先按此实现错误处理分支。

---

## 1. 编码规则

```
格式：  [2 位域码][3 位域内序号]  或  [3 位业务域][3 位状态码]
本文档采用后者：[3 位业务域][3 位状态码]
```

| 段位 | 含义 |
| --- | --- |
| 第 1-3 位 | 业务域 |
| 第 4-6 位 | 状态码 |

---

## 2. 通用状态码（第 4-6 位）

所有业务域共用这9 个状态码。

| 后 3 位 | HTTP | 含义 | 前端处理 |
| --- | --- | --- | --- |
| `000` | 200 | 成功 | 正常处理 |
| `001` | 400 | 参数错误 | Toast `message`，不重试 |
| `002` | 401 | 未认证 | 触发 token 刷新；失败则跳登录 |
| `003` | 403 | 无权限 | Toast「无权限」，不重试 |
| `004` | 404 | 资源不存在 | Toast `message` |
| `005` | 409 | 资源冲突 | Toast `message`，刷新列表 |
| `006` | 422 | 业务规则拒绝 | Toast `message`，**不重试** |
| `007` | 429 | 限流 | Toast「操作过于频繁」，读 `Retry-After` |
| `008` | 500 | 服务端错误 | Toast「服务异常」，可重试 1 次 |
| `009` | 503 | 服务不可用 | Toast「服务暂不可用」，可重试 |

**重试策略**：

| 状态码 | 是否重试 |
| --- | --- |
| `000` `001` `003` `004` `006` | ❌ 不重试（业务确定性错误） |
| `002` | 刷新 token 后重放 **1 次** |
| `005` | ❌ 不重试 |
| `007` | 按 `Retry-After` |
| `008` `009` | ✅ 指数退避重试最多 **2 次** |
| 网络错误 | ✅ 重试最多 3 次 |

## 4. 业务一致性错误（422 详解）

这类错误不是「参数不对」，而是「参数合法但业务不允许」。**前端必须给出明确提示，且不重试。**

| 场景 | code | 提示文案 |
| --- | --- | --- |
| 库存不足 | `120001` | 库存不足，当前库存：{stock} {unit} |
| 农事记录已审核 | `110004` | 农事记录已审核，不可修改 |
| 订单状态不允许流转 | `160002` | 订单当前状态为「{status}」，不支持该操作 |
| 该果树已认养 | `150004` | 该果树已被其他用户认养 |
| 该果树已挂牌 | `150021` | 该果树已挂牌，不可重复操作 |
| 证书重复开具 | `150031` | 证书已开具 |
| 收入构成不平衡 | `230001` | 收入构成合计 {sum} 与总额 {total} 不符 |

## 5. 前端错误处理规范

```javascript
// 统一处理（api-client.js 的 onResponse 拦截器）
ApiClient.onResponse(function (res, code) {
  if (code === 0) return res.data;

  if (code === 100002) {
    // 未认证 → 刷新 token 并重放（最多 1 次）
    return ApiClient.refreshToken().then(function () {
      return ApiClient.replay();
    });
  }

  if (code >= 120001 && code <= 120003) {
    // 库存类错误 → 高亮库存列并提示
    Toast.error(res.message);
    highlightStockCell();
    return Promise.reject(res);
  }

  if (code === 110004 || code === 160002) {
    // 状态不允许 → 提示并刷新列表
    Toast.error(res.message);
    refreshList();
    return Promise.reject(res);
  }

  if (code >= 200002 && code <= 200004) {
    // 文件类错误 → 提示清理存储
    Toast.error('存储空间不足，请在设置中清理缓存');
    return Promise.reject(res);
  }

  Toast.error(res.message);
  return Promise.reject(res);
});
```

**硬性要求**：

```
① 同一错误不重复弹toast（防连续点击产生多个提示）
② 4xx 类错误不重试，5xx 类最多重试 2 次
③ 业务一致性错误必须提示用户「怎么办」，不能只说「失败」
④ 用户数据不得因错误而丢失——写操作失败时表单内容必须保留
```

## 6. 错误码分配原则

新增错误码时遵循：

| 原则 | 说明 |
| --- | --- |
| **复用优先** | 先查是否已有合适的码，能复用就不新增 |
| **域内递增** | 新码在所属域内递增，不跨域借号 |
| **语义稳定** | 一个码的语义永不改变（否则前端分支会失效） |
| **带上下文** | 错误信息中应含具体值（库存数、状态名），便于前端直接展示 |
| **不暴露内部** | 不返回堆栈、SQL、内部路径 |

## 7. 当前无对应错误码的已知场景

以下场景在现有原型中无错误处理，接入后端时需补充错误码：

| 场景 | 现状 | 建议 code |
| --- | --- | --- |
| GPS 降级 | 前端静默降级为基准点 | `210010` / `210011`（仅上报） |
| 图片压缩失败 | `compressImage` 静默失败 | `200005` |
| 挂牌 PNG 归档跳过 | `skipped: true` 但无原因分类 | `200002` / `200006` |
| 追溯兜底映射 | ⚠️ **应删除兜底**，改为 `140003` | `140003` |
| 病虫害置信度低 | 无提示，直接展示结果 | `170010` |
