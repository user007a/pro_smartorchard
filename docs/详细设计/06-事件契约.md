# 06 · 事件契约

> **本章作用**：定义数据变更后「谁需要知道、怎么知道、收到后做什么」。
> **本章解决一个具体问题**：本项目有大量页面直接监听 `storage` 事件，但用法各不相同，导致同一份数据在不同页面表现不一致。本章把事件统一为可判定的契约。

---

## 1. 事件体系总览

本项目共有 **3 类事件**：

```
① storage 事件           浏览器原生 · 跨标签页/跨窗口
② Store 自定义事件       xxxStoreChange · 同窗口内跨文档（含 iframe）
③ 网络状态事件           online / offline · MobileStore 专用
```

另有1 个 UI 事件：`typography:ready`（[typography.js](file:///d:/dev/pro_smartorchard/html/applefarm_backhand/js/typography.js#L108) 派发）。

### 1.1 三类事件的边界（必须理解）

| 事件 | 触发时机 | 通知范围 | **不通知** |
| --- | --- | --- | --- |
| `storage` | 其他标签页/窗口写入 localStorage | 同源的其他 browsing context | ⚠️ **不通知写入方自己** |
| `xxxStoreChange` | 本窗口内 Store 写入后 | 同窗口的所有文档（含 iframe 子页面） | 跨标签页 |
| `online` / `offline` | 网络状态变化 | 当前页面 | — |

> **⚠️ 最常见的错误**：以为 `storage` 事件能在「当前页面自己」触发。**它不会。**
> 同一个页面内 Store 写入后要刷新 UI，必须靠 `subscribe()` 或自定义事件。
> 若只监听 `storage`，写入方页面永远不会自动刷新。

## 2. `storage` 事件契约

### 2.1 浏览器原生语义

```javascript
window.addEventListener('storage', function (e) {
  e.key      // 变化的键名；clear() 时为 null
  e.oldValue // 旧值
  e.newValue // 新值
  e.storageArea // localStorage 或 sessionStorage
  e.url      // 发生变化的文档 URL
});
```

**必须记住的三条限制**：

```
① 只在其他标签页/窗口触发，当前窗口不触发
② 不在同一个 iframe 内的父文档触发（父页面与 iframe 属于不同 context，但同源iframe
   的父文档能收到 iframe 内写入的 storage 事件？—— 不能。storage 只通知
   顶层浏览上下文之外的同源上下文。PC 后台是 iframe 结构，必须靠自定义事件。
③ e.newValue 在 value 变化时才填充
```

### 2.2 本项目的两种正确用法

**用法 A：Store 内部同步内存态（必须）**

5 个有订阅机制的 Store 都在 `storage` 监听中调用 `_syncFromExternal()`：

```javascript
// biz-store.js L271
window.addEventListener('storage', function (e) {
  if (e.key === STORAGE_KEY) BizStore._syncFromExternal();
});
```

作用：其他标签页改了数据 → 本标签页的 `inMemory` 同步刷新 → `notify()` 通知本页订阅者重渲染。

**用法 B：页面按 key 直接响应（可选）**

```javascript
// da_alert.html L1103 / patrol_route.html L699 等
window.addEventListener('storage', function (e) {
  if (e.key !== 'applefarm_alert_state_v1') return;
  render();
});
```

### 2.3 实测：监听 `storage` 的35 处位置

| 端 | 文件 | 数量 |
| --- | --- | --- |
| Store 内部 | `biz-store.js` / `data-store.js` / `trace-stat-store.js` / `alert-data.js` / `device-store.js` / `mobile-store.js` | 6 |
| 大屏 | `da_alert` / `da_business` / `da_dashboard` / `da_overview` | 4 |
| 移动端 | `mb_ai_assistant` / `mb_disease` / `mb_adoption_browse` / `mb_map` / `mb_adoption_tagging` / `mb_adoption_cert` / `mb_patrol` / `mb_label` / `mb_material` / `mb_home` / `mb_record_task` / `mb_troubleshoot` | 12 |
| H5 | `h5_member` / `h5_adoption` / `h5_profile` | 3 |
| PC 后台 | `adoption_farming` / `index` / `mb_ai_config` / `mb_disease_config` / `mb_sync_queue` / `patrol_route` | 6 |
| H5 数据层 | `trace-stages.js` / `mall-coupons.js` / `mall-promotions.js` / `mall-products.js` | 4 |

> **⚠️ 合规风险**：这 35 处监听各自手写 `if (e.key !== 'xxx') return;`，**没有统一的 key 常量引用**。改key 名时必然漏改。
> 改造建议：全部改为通过 Store 的 `subscribe()` 订阅，禁止页面直接监听 `storage`。

## 3. Store 自定义事件契约

### 3.1 五个事件名

| 契约号 | 事件名 | Store | payload | 派发位置 |
| --- | --- | --- | --- | --- |
| EVT-STORE-001 | `bizStoreChange` | `BizStore` | `{reason}` | biz-store.js L187 |
| EVT-STORE-002 | `dataStoreChange` | `DataStore` | `{reason}` | data-store.js L153 |
| EVT-STORE-003 | `traceStatStoreChange` | `TraceStatStore` | `{reason}` | trace-stat-store.js L149 |
| EVT-STORE-004 | `alertStoreChange` | `AlertStore` | `{reason}` | alert-data.js L182 |
| EVT-STORE-005 | `deviceStoreChange` | `DeviceStore` | `{reason}` | device-store.js L347 |
| — | ⚠️ **无** | `MaterialStore` | — | — |

**命名规范**：`{store名去掉Store后缀}StoreChange`，全小写驼峰。

### 3.2 统一的 broadcast 三步式

5 个 Store 的实现完全一致：

```javascript
function broadcast(reason) {
  save();                    // ① 落盘
  notify(reason);            // ② 通知本页 subscribe() 订阅者
  try {
    window.dispatchEvent(new CustomEvent('xxxStoreChange',
      { detail: { reason: reason } }));
  } catch (e) {}             // ③ 通知同窗口其他文档（含 iframe）
}
```

> `alertStoreChange` 与 `deviceStoreChange` 的注释明确写为「跨 iframe（同 origin）通过自定义事件」——**这正是 PC 后台 iframe 架构下的关键机制**。

### 3.3 `reason` 取值契约

`reason` 是判断「这次变更是什么」的依据，各Store 取值如下：

| Store | reason 取值 | 触发场景 |
| --- | --- | --- |
| `BizStore` | `'init'` / `'revenueMix'` / `'receivable'` / `'metrics'` / `'reset'` / `'sync'` | 见下|
| `DataStore` | `'init'` / `'sources'` / `'models'` / `'reset'` / `'sync'` | — |
| `TraceStatStore` | `'init'` / `'reset'` / `'sync'` 等 | — |
| `AlertStore` | `'init'` / `'reset'` / `'sync'` / `'status:{id}'` / `'history:{id}'` | ⚠️ **后两者带 id** |
| `DeviceStore` | `'init'` / `'access'` / `'gateway'` / `'camera'` / `'reset'` / `'sync'` | — |

> **⚠️ `AlertStore` 的 reason 格式不统一**：状态变更时是 `status:<id>`，历史追加时是 `history:<id>`，其他是裸字符串。订阅方若要按 reason 分支处理，必须用 `indexOf(':')` 解析。建议统一为 `{action, id}` 结构（列入遗留 L-D10）。

### 3.4 订阅规范

**必须**：用 `subscribe()` 而非 `addEventListener` 监听 Store 变更。

```javascript
// 正确
var unsubscribe = BizStore.subscribe(function (reason) {
  render(reason);
});
// 页面卸载时
window.addEventListener('beforeunload', function () { unsubscribe(); });

// 错误：只监听 storage，当前窗口写入方自己收不到
window.addEventListener('storage', function (e) {
  if (e.key === 'applefarm_biz_v1') render();
});
```

**`subscribe()` 的两个特性**（依赖它们才不会漏首屏）：

| 特性 | 说明 |
| --- | --- |
| **注册即回调一次** | `subscribe(fn)` 内部会立即 `fn('init')`，所以首屏数据与后续变更用同一个回调处理 |
| **返回 unsubscribe** | 必须保存并在页面卸载时调用，否则闭包泄漏 |

**反模式**：

```javascript
// 错误：只监听 storage，同页写入不刷新
Store.setXxx(v);   // 页面自己改的数据，表格不会更新

// 错误：不 unsubscribe，反复进入页面导致回调累积
Store.subscribe(render);   // 每次进页面都注册一次

// 错误：在 storage 回调里再写 Store，造成循环广播
window.addEventListener('storage', function(e){ if(...) { Store.setYyy(1); } });
```

## 4. 网络状态事件（移动端专用）

| 契约号 | 事件 | 监听位置 | 处理 |
| --- | --- | --- | --- |
| EVT-NET-001 | `online` | mobile-store.js L410 | 提示「网络已恢复」；`pending() > 0` 时 toast 后触发 `flush()`；否则 toast「网络已恢复」 |
| EVT-NET-002 | `offline` | mobile-store.js L411 | toast「网络已断开，将转为离线暂存」 |

两者最终都调用 `emit('network')` 通知 `MobileStore.subscribe()` 的订阅者。

**判定标准**：`navigator.onLine !== false` 视为在线（`isOnline()`）。**注意 `navigator.onLine` 只表示是否有网络连接，不表示是否真的能访问后端**——所以 `flush()` 的成功与否必须以请求结果为准，不能以 `onLine` 为准。

## 6. 同步状态栏的渲染事件

移动端 F-282 同步状态栏由 `MobileStore.renderSyncBar(el)` 渲染。

**状态机**（4 态）：

| 状态 | 判定 | 文案 | CSS class |
| --- | --- | --- | --- |
| `offline` | `!online` | `离线 · N 条待同步` / `当前离线` | `.is-offline` |
| `syncing` | `online && syncing` | `同步中…` | `.is-syncing` |
| `pending` | `online && n > 0` | `N 条待同步` | `.is-pending` |
| `done` | `online && n === 0` | `数据已同步` | `.is-done` |

**重绘触发点**：

```
① 初次 renderSyncBar(el)   → paint() 一次
② onQueueChange 订阅      → 队列变化时 paint()
③ online / offline 事件    → onNetworkChange → emitQueue → paint()
④ 点击「立即同步」按钮      → 委托监听 data-sync-now 属性 → flush()
```

**「立即同步」按钮的显示条件**：`n > 0 && online`。离线时不显示（无法同步）。

## 7. 事件契约的三个禁止项

| 禁止 | 原因 |
| --- | --- |
| **禁止页面用 `addEventListener('storage')` 作为唯一的数据刷新手段** | 当前窗口写入方收不到，会出现「改了数据表格不刷新」 |
| **禁止在 `storage` / 自定义事件回调里写入同一个 Store** | 会触发无限循环广播，页面卡死 |
| **禁止不 unsubscribe** | 内存泄漏 + 回调累积导致渲染多次 |

## 9. 生产替换点（接入后端）

| # | 现状 | 目标 | 改动点 |
| --- | --- | --- | --- |
| 1 | `storage` 事件实现跨页同步 | SSE / WebSocket 推送 | Store 的 `subscribe()` 内部改为订阅服务端推送，**页面无需改动** |
| 2 | `MobileStore.simulateUpload` 模拟上传 | 真实 HTTP | 替换 `simulateUpload` 一处，队列/重试/去重不动 |
| 3 | `online`/`offline` 判定网络 | 保留 + 增加请求失败重试 | `flush()` 增加真实失败判定 |

**关键结论**：事件体系的生产替换**收敛在 Store 内部**，页面层的订阅代码不用改。这与 `04-存储契约.md` §8 的替换点 1-4 是同一批。
