# 智慧果园平台 · 数据设计约定

> 本文档是「原型 → 正式项目」开发过程中的**数据层设计铁律**。
> 它面向两类读者：**业务方（用于验收）** 与 **AI（用于执行）**。
> 一切数据库建表、接口设计、字段存储，都必须遵守本文档；遇到本文档未覆盖的情况，**以本文档的规则精神类推**，不得擅自违背。

---

## 〇、一句话总原则

> **字段以原型为准；界面 1:1 复刻原型；数据全部落库；下拉存编码、关联存 ID、数值与日期拆结构化；唯一性靠数据库约束保证。**

---

## 一、权威优先级

当「原型页面」「需求说明书」「本文档」三者描述不一致时，按以下顺序裁决：

1. **原型页面**（最高权威——验收标准就是原型）
2. **本文档**（数据设计的统一规则）
3. **需求说明书**（仅作参考，用于补充业务背景）

> 落地动作：动手写任何代码前，先做一次「字段盘点」，把原型真实字段与需求说明书字段字典逐项比对，产出《字段差异清单》交由业务方确认；确认后以「原型 + 本文档」为唯一依据。

## 二、字段盘点表 · 统一模板

每对一个页面做字段盘点，都输出如下列的一张表（颗粒度 = 逐字段）：

| 列 | 含义 |
|---|---|
| 字段 | 字段英文名（入库字段名） |
| label | 界面显示的中文名 |
| 控件类型 | text / number / date / select / textarea / image 等 |
| 枚举？ | 是否为下拉/固定选项（✅ 是 / 否） |
| 引用来源 | 该字段的值来自哪里（见第四节） |
| 约束 | 是否唯一、必填、外键等 |
| 建议存储 | 数据库类型与存储方式 |

示例（地块管理页）：

| 字段 | label | 控件类型 | 枚举？ | 引用来源 | 约束 | 建议存储 |
|---|---|---|---|---|---|---|
| name | 地块名称 | text | 否 | 无 | **唯一** | varchar + 唯一约束 |
| baseId | 所属基地 | select | 否 | → 基地表 base.id | 外键 | 存 base_id |
| variety | 果树品种 | select | ✅ 是 | → 字典表（品种） | 外键 | 存字典编码 |
| managerId | 负责人 | select | 否 | → 用户表 user.id | 外键 | 存 user_id |

## 三、五条存储铁律

### 铁律 1：枚举 / 下拉字段 → 一律建「字典表」

凡是「下拉选择 / 固定选项」的字段，数据库**存编码（code）**，界面**显示中文（label）**，对应关系统一放在字典表 `dict` 中。

```
字典表 dict 结构示意：
  dict_type = 'enterprise_type'（企业类型）
    code=1, label=有限责任公司
    code=2, label=股份有限公司
    code=3, label=农民专业合作社
    ...
```

**好处：**
- 以后要新增/修改一个下拉选项，只改字典表一行，**所有引用该下拉的页面自动生效**，无需逐个改页面。
- 数据可结构化统计、筛选、排序。

**适用例子（已确认）：** 企业类型、经营状态、角色分类、顶部显示（是/否）、证书状态机、果树品种等。

### 铁律 2：数值字段 → 存数字，不存带单位的文本

反例（原型现状，需纠正）：
- `注册资本` 存成了字符串 `"11250"` → 应存数字 `11250`，单位"万元"另作处理。
- `经营数值` 存成了 `"12860"` + 文本 `"万元"` → 应拆成「数值 decimal + 单位字段」。

**规则：** 数字就是数字，单位要么单独一个字段存，要么归入字典表，**绝不把「数字+单位」拼成一个字符串**。否则无法排序、求和、比较。

### 铁律 3：日期/日期区间 → 拆成标准日期字段

反例（原型现状，需纠正）：
- `营业期限` 存成了 `"2010年10月11日 至 长期"`（一句话文本） → 应拆成 `term_start`（date）+ `term_end`（date，长期可空或特殊标记）。

**规则：** 起止日期分开存，禁止把两个日期拼成一句文本。

### 铁律 4：图片/附件 → 上传到文件系统，业务表只存「文件 ID」

- 图片（证书扫描件、专家头像、横幅背景等）、视频、文件/附件（CSV、PDF 等）一律通过「文件上传」接口保存为服务器上的文件。
- **禁止**把图片以 base64 字符串塞进数据库字段（原型现状用了 `readAsDataURL`，需纠正）。

**存「文件 ID」而非「完整 URL」（关键）：**

- 数据库业务表只存 `file_id`（文件 ID），**不存完整 URL 地址**（如 `https://.../cert.jpg`）。
- 展示时，前端根据 `file_id` 动态拼出当前可访问的 URL（如 `/api/file/{file_id}`）。

**为什么存 ID 不存 URL：**
1. 域名/服务器地址会变（内网 → 云），写死的 URL 迁移即失效；
2. 文件存储位置会换（本地磁盘 → OSS），存 ID 则业务数据无需改动；
3. 同一 ID 可灵活输出原图/缩略图/下载等多种形态。

**统一文件模型：一张「文件表」`sf_file`**

```
sf_file：
  id            文件 ID（主键）
  file_name     原始文件名（如 cert_01.jpg）
  file_type     类型：image / video / document
  file_size     大小（字节）
  store_path    实际存储路径（真实地址，仅后端知晓）
  created_at    上传时间
```

- 业务表（如 `sf_cert`）只存 `file_id`，指向 `sf_file.id`；
- 真实地址 `store_path` **只存在 `sf_file` 一张表**，业务表永远不碰地址；
- 将来换存储位置，只改 `sf_file` 或后端映射，其他业务表零改动。

> **一句话**：业务表存"文件的身份证号（file_id）"，文件的"家庭住址（真实路径）"只登记在文件表一张表里——因为地址会变，身份证号不会变。

### 铁律 5：唯一性 → 用数据库「唯一约束」保证，不靠人工自觉

- 例如「地块名称」「基地名称」必须唯一。
- 做法：数据库对应字段加**唯一约束（unique）**，系统在写入时自动拦截重复值并提示业务人员。
- 业务人员「看了就明白」的友好报错：例如「基地名称已存在，请更换」。

### 铁律 6：命名避开 MySQL 关键字（保留字）

表名、字段名**不得裸用 MySQL 保留字**（如 `order`、`group`、`user`、`key`、`desc`、`type`、`table`、`index`、`date`、`from`、`to`、`count`、`level`、`rank`、`name`、`status` 等），否则会导致 SQL 报错、框架歧义、排查困难。

**三条具体规则：**

1. **表名统一加业务前缀**：`sf_`（SmartFarm 缩写），例如：
   - `sf_enterprise`（企业信息）、`sf_plot`（地块）、`sf_base`（基地）、`sf_user`（用户）、`sf_cert`（资质证书）、`sf_order`（订单）、`sf_dict`（字典）。
   - 加前缀后，`order`、`user` 等裸关键字不再冲突；且一眼可识别为本项目表，不与系统表/第三方表混淆。

2. **字段名一律「小写 + 下划线」**，并带业务语义，禁止裸用关键字：
   - 描述字段 → `description` / `remark` / `note`，**不用 `desc`**；
   - 类型字段 → `enterprise_type`、`cert_type`，**不用裸 `type`**；
   - 状态字段 → 统一用 `xx_status`（如 `order_status`），**不用裸 `status`**；
   - 排序字段 → `sort_order`，**不用 `order`**；
   - 分组字段 → `category` 或 `xx_group`，**不用裸 `group`**。

3. **公共字段统一命名**（所有表一致，便于阅读与复用）：
   - 主键：`id`（bigint 自增）；
   - 创建时间：`created_at`；更新时间：`updated_at`；
   - 逻辑删除标记：`is_deleted`（0=否，1=是）；
   - 排序：`sort_order`；备注：`remark`。

> **一句话**：表名加 `sf_` 前缀 + 字段名带业务语义（不裸用 order/desc/key/type/group/user 等词），即可彻底避开关键字冲突，AI 也无需纠结反引号。

### 铁律 7：每张业务表必须带「公共字段」（原型不画，但数据库必须有）

原型页面上**不会画出**创建时间、更新时间、删除标志等字段，但它们是**技术底座字段**，**每张业务表都必须有**。区分两类字段：

| 类别 | 是否在原型界面显示 | 说明 |
|---|---|---|
| **业务字段** | ✅ 显示 | 来自原型，如企业名称、地块名称、负责人 |
| **公共字段** | ❌ 不显示 | 数据库必须有，用于数据治理 |

**公共字段清单（每张业务表强制包含）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint 自增 | 主键 |
| `created_at` | datetime | 创建时间（录入时自动写入） |
| `updated_at` | datetime | 更新时间（修改时自动更新） |
| `is_deleted` | tinyint | 逻辑删除标记：0=正常，1=已删除 |
| `sort_order`（可选） | int | 排序号 |
| `remark`（可选） | varchar/text | 备注 |

**逻辑删除铁律（对本项目是刚需）：**

- **所有业务表删除一律用「逻辑删除」**（`is_deleted = 1` 标记），**禁止物理删除**（真删数据）。
- 界面上点「删除」只是把 `is_deleted` 置 1，数据仍留在库中，仅不再显示。
- **为什么必须逻辑删除：**
  1. **误删可恢复**：业务人员误删后可找回，物理删除则永久丢失；
  2. **溯源完整**：本项目核心卖点是「溯源」，历史数据被物理删除会断链，属业务致命伤；
  3. **审计合规**：可追溯「谁在何时删除了什么」。
- 后端所有查询默认过滤 `is_deleted = 0`，被删除的数据对业务人员"不可见但存在"。

## 三·五、数据库高级设计决策（索引 / 外键 / 视图 / 日志）

### 决策 0：建表脚本的分阶段策略（防误删数据）

- **初期开发阶段**：建表脚本（`schema.sql`）可用 `DROP TABLE IF EXISTS` + `CREATE`，便于反复调整表结构时直接重跑。
- **系统上线 / 表内有真实数据后**：**禁止再使用 `DROP TABLE`**，改表结构必须用「增量迁移」（`ALTER TABLE ... ADD COLUMN` 等只加不删），避免清空真实数据。
- AI 每次改动表结构，必须说明「是重建（仅限初期）还是增量迁移」。

### 决策 1：索引——「少而准」，只建三类

| 场景 | 例子 | 索引 |
|---|---|---|
| 外键字段（关联用） | `plot.base_id`、`cert.file_id` | 普通索引 |
| 高频查询/筛选字段 | `order.order_status`、`user.phone` | 普通索引 |
| 唯一约束字段 | `plot.name` | 唯一索引（自动含索引） |

**明确不做：** 不给所有字段建索引；初期不搞联合索引、全文索引（等真遇到慢查询再加）。

### 决策 2：外键——「逻辑外键要，物理外键约束不要，唯一约束一定要」

- **逻辑外键（必须）**：字段存关联表的 ID，语义上关联（如 `plot.base_id`）。
- **物理外键约束（建议不加）**：不在建表时声明 `FOREIGN KEY`，原因：
  1. 有物理外键时，删除被引用记录会强制校验、卡住删除流程，与「逻辑删除」别扭；
  2. AI 批量建表/后期改结构时，外键依赖顺序极易报错，徒增排错成本；
  3. 已有「逻辑删除 + 前端只提供真实存在的选项」兜底，脏数据难进入。
- **唯一约束（必须加）**：防止"重复名称"这类低级错误，代价小、收益大。

> **业务方确认（2026-11-11）**：表之间**一律不加物理外键约束**，通过页面增删改查灵活组织数据；仅保留「唯一约束」。此为准绳，AI 建表时不得擅自添加 `FOREIGN KEY`。

### 决策 3：视图——初期不建

- 数据量小、查询全由后端 API 统一编写，业务人员不直接写 SQL，视图价值低。
- 需要多表联合展示时（如地块列表显示"基地名 + 负责人名"），由**后端接口做 join** 返回结果，更直观、更好改、AI 更好生成。

### 决策 4：埋点/操作日志——必须做，但用「一张通用日志表」最简方案

本项目溯源是核心卖点 + 多人协同，必须留痕。分两档：

**第一档（现在做，够用）：通用操作日志表 `sf_operation_log`**

```
sf_operation_log：
  id            日志 ID
  user_id       操作人
  module        模块（如"地块管理""农事记录"）
  action        动作（新增/修改/删除/导出/登录）
  target_id     操作对象 ID
  detail        简要描述（改了什么，JSON 或文本）
  ip            来源 IP
  created_at    时间
```

- 所有「增删改、导出、登录」等关键操作，后端自动写入一条。
- 因采用逻辑删除，被删数据仍在，日志可对上"谁删的"。

**第二档（以后需要再上）：字段级差异记录**（精确到"某字段从 A 改成 B"），初期不做，避免过度设计。

### 决策 5：权限粒度——只做到「模块级」，不做按钮级/字段级

- 权限做到「模块 → 查看 / 新增 / 编辑 / 删除 / 导出」这一**粗粒度**即可。
- **不做**按钮级、字段级精细权限。
- **原因（业务方确认）**：系统用户是农业企业人员，管理粒度若细到按钮级，系统上线即沦为摆设、无人使用。中小企业落地应以「够用、易用、好维护」为优先。

### 决策 6：脚本「单一数据源」——schema/seed 只存一份

- `schema.sql`、`seed.sql` **唯一权威位置是 `server/db/`**，Docker 启动与后端迁移都读这里。
- `docs/` 下**不重复存放 SQL 文件**，只放 `.md` 文档；需要查阅表结构时看《核心数据模型.md》即可。
- 杜绝「server 与 docs 两份脚本不一致」的隐患。

### 决策 7：Docker 最小推送——镜像只含运行必需，不含文档

- **必须进镜像**：`html/`（前端页面）、`server/`（后端代码）、`server/db/schema.sql` + `seed.sql`、`server/package.json`。
- **绝不进镜像**：`docs/`（需求/设计/宣传稿等内部文档）、`.git/`、`server/uploads/`（真实数据，走 volume 挂载）、`node_modules/`。
- 用 `.dockerignore` 自动排除（`.git`、`docs`、`node_modules`、`server/uploads`、`*.md` 等），保证镜像最小、且不泄露内部文档。

## 四、字段的「引用来源」三分法

凡是一个字段的值「来自别的地方」，都属于「引用」，按来源分三类，建表方式不同：

| 类型 | 含义 | 例子 | 存储方式 |
|---|---|---|---|
| **字典型基础数据** | 相对固定的枚举值，有独立页面/字典维护 | 果树品种、企业类型、经营状态 | 存字典编码（外键指向 dict） |
| **业务实体引用** | 活的数据，来自其他业务表 | 所属基地（→基地表）、负责人（→用户表） | 存对应表的主键 ID（外键） |
| **本表普通字段** | 无引用，直接录入 | 地块名称、地址 | 直接存 |

### 引用字段的通用规则

1. **存 ID，不存文字。** 例：`地块.所属基地` 存 `base_id`，不存"一号基地"三个字。
   - 好处：被引用方改名后，引用方自动显示新名字；防止删掉被引用方后留下"幽灵文字"。
2. **必须加外键约束。** 例：`地块.base_id` 必须存在于 `base.id`，否则数据库拒绝写入（防脏数据）。
3. **区分「字典」还是「实体」：**
   - 值少、变化不频繁 → 字典表（有后台页面统一维护）；
   - 值多、有完整增删改查、本身就是业务对象 → 独立业务表，被引用方存其 ID。

## 四·五、字段校验的分层规则（手机号 / 密码 / 邮箱 / 身份证等）

> 针对「手机号、密码、邮箱、身份证号」等**通用常识校验**（非业务规则），采用**分层设防**，职责各管一段，避免 AI 全塞前端（不安全）或乱塞数据库（难维护）。

### 分层原则

```
用户输入 →【前端】格式即时校验（体验层）
        →【后端】格式再校验 + 业务校验（安全层，不可绕过）
        →【数据库】类型/长度/唯一硬约束（结构层，最后兜底）
```

### 逐字段约定

| 字段 | 前端校验 | 后端校验 | 数据库约束 |
|---|---|---|---|
| 手机号 | 11 位、1 开头，即时提示 | 同前端正则再验（必须） | `varchar(11)` + **唯一索引** |
| 密码 | 提示强度规则（长度、复杂度） | 校验强度 | **只存哈希值，绝不存明文**（如 bcrypt） |
| 联系邮箱 | 校验 `xx@xx.xx` 格式 | 同前端正则再验 | `varchar`（可选唯一） |
| 身份证号 | 校验 18 位（可选校验位算法） | 校验 18 位 | `varchar(18)`，敏感信息需加密/脱敏存储 |

### 核心规则

1. **格式校验（是否 11 位、是否含 @）→ 放前端 + 后端，不放数据库。**
   - 数据库能力有限：只能管"类型、长度、唯一"，不会判断业务格式；
   - 格式规则会变（新号段、国际区号），改后端一行代码即可，写进库约束则难改。
2. **数据库只做硬性结构约束**：类型、长度、唯一、非空。
3. **密码必须哈希存储**（bcrypt 等），**任何情况下不存明文**——这是安全红线。
4. **敏感信息（身份证、手机号）按需求说明书要求「脱敏展示、按需解密」**，存储层可加密，具体方案单独约定。

要正确设计数据库，必须先摸清**全系统的「基础数据表」与「业务实体表」及其关联关系**。已识别到的典型关联（示例）：

- 地块 → 基地（所属基地）、用户（负责人）、品种（果树品种）
- 农事记录 → 地块、人员、任务
- 认养订单 → 果树、消费者、基地
- 设备 → 基地、地块、网关
- ……

> 动作：从「基地 / 地块 / 用户 / 品种」这几个**互相引用的地基模块**开始，先画出**核心数据关系图（ER 图）**，把关联关系定清楚，再逐步铺开到全模块。

---

## 六、原型改动的应对原则

原型后续若有小改动，按以下原则处理，避免牵一发动全身：

1. **界面改动（改文案/布局/加按钮）** → 只改对应 HTML，通常不动后端与数据库。
2. **新增/删除数据字段** → 需同步改：数据库表结构 + 后端接口 + 字段盘点表。
3. **改动完成后，AI 必须说明**「这次改了哪些文件、是否动了数据库结构」，便于业务方评估影响范围。

> 核心保障：**界面层与数据层分离**。分离了，改界面就不会伤到数据。

---

## 七、开发节奏与验收方式（对齐业务方习惯）

1. **一次只做一个模块**，做完当场验收，不搞一次性全量生成（避免无法逐项核对）。
2. **每个功能给出「演示路径」**：例如「验证农事记录入库：打开 farming_record 页 → 新增一条 → 刷新仍在（说明入库）→ 打开移动端对应页可见同一条（说明跨端打通）」。
3. **数据落库可视化验证**：每次改动后，展示数据库表里的真实数据（或通过网页版数据库查看工具），让业务方直观确认「数据真的进库了、字段对得上」。
4. **验收契约 = 四列对照表**（原型页 ↔ 功能 ↔ 接口 ↔ 数据库表），业务方逐页打勾。
