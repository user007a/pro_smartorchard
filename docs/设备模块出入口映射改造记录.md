# 设备模块出入口映射改造记录（策略 A 落地）

> 本文档记录设备模块「store ↔ 数据表」出入口映射层的实现，作为其余 16 个模块照此执行的技术样板。

---

## 一、改造目标与结论

把设备模块从「localStorage 持久化」切换为「MySQL 持久化」，**保持页面代码零改动**、store 内部逻辑零改动。

**核心成果**（已完成并验证通过）：

| 产出 | 文件 | 状态 |
|---|---|---|
| 后端聚合读写接口 | `server/routes/device-aggregate.js` | ✅ 端到端验证 |
| 前端映射层 | `html/applefarm_backhand/js/shared/device-mapper.js` | ✅ 双向转换验证 |
| store 出入口桥接 | `html/applefarm_backhand/js/shared/device-store.js` | ✅ 语法通过 |
| 登录接后端 | `html/applefarm_backhand/login.html` | ✅ 后端优先+本地回退 |
| 静态托管 | `server/app.js`（express.static html） | ✅ 页面/API 同源 |
| 设备外键回填 | `server/db/seed.sql` | ✅ 30 台设备 base_id/plot_id |

## 二、架构设计

### 2.1 同步 store 与异步后端的桥接

store 是**同步读**（页面直接 `DeviceStore.devices()`），后端是**异步**。桥接方案：

```
页面同步调用 DeviceStore.xxx()  ← 内存 inMemory（不变）
        │
        ├─ ensure() 首次调用时，setTimeout 触发 preloadFromBackend()
        │    → Api.get('device/aggregate') → DeviceMapper.toAggregate() → 替换 inMemory → notify('backend-sync')
        │
        └─ save()（同步写 localStorage 后）→ persistToBackend() 防抖 300ms
             → DeviceMapper.fromAggregate() → Api.create('device/aggregate') → 落 MySQL
```

- **后端不可用/未登录**：`backendEnabled()` 为 false，自动回退 localStorage，原型仍可运行。
- **防重入**：`preloadTriggered` / `backendLoadPromise` / `persistTimer` 三重保护。

### 2.2 依赖自动加载

`device-store.js` 顶部 `ensureDeps()` 用 `document.createElement('script')` 同步注入：
- `../../../common/js/api.js`（统一 fetch 封装）
- `device-mapper.js`（字段映射层）

→ 已引用 device-store.js 的 18 个页面**无需逐页加 script 标签**。

## 三、字段映射要点（13 张表）

### 3.1 主键语义

- store `item.id`（业务编号 D-001/AC-001/M-001…）↔ 表 `*_code` 唯一列
- 物理主键自增 `id` 由后端管理，前端不感知

### 3.2 关键字段转换

| 类别 | store → 表 | 说明 |
|---|---|---|
| 驼峰↔下划线 | `deviceName` → `device_name` | 逐字段映射 |
| 金额单位 | `purchaseAmount`(万元) → `purchase_amount`(元) | ×10000 |
| 布尔 | `ptz: true` → `has_ptz: 1` | TINYINT |
| 数组 | `points: [...]` → `measure_points: "a,b,c"` | 逗号串（物模型测点拆子表） |
| 枚举 | `status: 'online'` → `run_status: 'online'` | 状态值本身已是英文 code，直接映射 |

### 3.3 枚举值归一（store 中文 ↔ 表英文）

| 实体 | store | 表 |
|---|---|---|
| 接入状态 | online/warning/offline | connected/abnormal/disconnected |
| 网关状态 | online/warning/offline | running/unstable/offline |
| 视频状态 | online/warning/offline | online/weak/offline |
| 盘点状态 | draft/checking/done/abnormal | pending/checking/done/loss |
| 审计类型 | create/update/delete/status | 新增/修改/删除/状态变更 |
| 日志级别 | info/warn/error/debug | INFO/WARN/ERROR/DEBUG |

### 3.4 外键引用（编号 ↔ 自增 id）

| 外键 | 业务键 | 解析 |
|---|---|---|
| `base_id` | 基地名（全称「天水麦积区基地」↔ 简称「麦积基地」） | `normalizeBaseName()` 归一 |
| `plot_id` | 地块编号（D-001 等，= sf_plot.code） | 直接匹配 |
| `device_id` | 设备编号（D-001 等，= sf_device.device_code） | 直接匹配 |
| `gateway_id` | 网关编号（GW-001） | 直接匹配 |
| `device_type_id` | 类型编码（weather_station） | 直接匹配 |

**双重保障**：前端 mapper 有 refs 时先解析为数字 id；后端聚合接口收到字符串时再兜底解析（`makeIdResolver` / `makeBaseResolver`）。

## 四、物模型 1:N 拆解

`models`（store 子数组）↔ `sf_device_type`（主表）+ `sf_device_measure`（测点子表）：

- **load**：按 `device_type_id` 分组 measure → 合并进 model 的 `points[]`
- **save**：每个 model 的 `points[]` 拆成一条 measure，带 `_typeCode` 回填 `device_type_id`

## 五、逻辑删除的统一处理（2026-11-11 修正）

早期版本中，设备模块的 3 张子表（`sf_device_measure` / `sf_device_log` / `sf_device_audit`）没有 `is_deleted` 列，
后端靠硬编码白名单 `NO_SOFT_DELETE` 特判。其余 9 张表（如 `sf_permission`、`sf_notification`、`sf_file`）
同样缺这列，导致通用 CRUD 一律返回 400（`Unknown column 'is_deleted' in 'where clause'`）。

**现已统一修正**：

1. **schema 层**：131 张表全部补齐 `created_at` / `updated_at` / `is_deleted`，
   符合《数据设计约定》铁律 7，不再有"局部例外"。
2. **代码层**：新增 `server/utils/table-meta.js`，运行时从 `information_schema`
   读取列清单来判断某表是否支持逻辑删除，**新增表无需改代码**。
   `crud.js` 与 `device-aggregate.js` 均已改为动态判断，不再有硬编码表名清单。
3. **只读保护**：`sf_device_log` / `sf_device_audit` / `sf_trace_query_log` / `sf_operation_log`
   标记为只读资源（`resources.js`），禁止通过通用 CRUD 写入或删除。

> 通用约定：无 `is_deleted` 列的表禁止删除接口（返回 400），符合"一律逻辑删除、禁止物理删除"的铁律。

## 六、遗留问题与后续

### 6.1 已修复：设备外键 NULL

seed 阶段设备表的 `base_id`/`plot_id` 未填充（全 NULL），已从 store 的 `DEVICE_SEED` 提取 base/plotId 映射，回填 30 台设备（30 台有 base，9 台有 plot），并同步回写 `seed.sql`。

### 6.2 待办（其余 16 模块）

按 `docs/store与数据表映射规范.md` 第七节清单逐模块执行，复用本样板的：
1. `device-aggregate.js` 的聚合读写模式（每模块一个聚合接口）
2. `device-mapper.js` 的映射模式（每模块一个 mapper）
3. store 出入口桥接（load/save 注入 preload/persist）

### 6.3 已知限制

- **防抖 300ms**：save() 后 300ms 才真正落库，极端情况下（立即刷新）可能丢最后 300ms 内的写。后续可改为「beforeunload 时 flush」。
- **全量 upsert**：每次 save 全量推送 13 张表，数据量大时性能需评估，可改为增量（只推变更的实体）。
- **base 名称口径**：store 全称 ↔ 表简称，靠 `normalizeBaseName` 归一，新增基地时需同步维护 `BASE_FULL_MAP`。
- **软删记录重新入库**：已修复——upsert 时强制 `is_deleted = 0`，避免被软删的记录再次保存后仍处于"已删除"状态。
